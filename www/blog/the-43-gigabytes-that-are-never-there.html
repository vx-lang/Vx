The 43 gigabytes that are never there

Aditya Kumar · 21 September 2026

TL;DR — Add up every tensor a Llama-2-7B prefill puts on the GPU and you get 58.93 GiB. An A100-40 has 40, so the model does not fit and you start offloading layers to the host. The tensors that are resident at the same time peak at 15.94 GiB, which is 39.8% of the card. The gap between those two numbers is 42.99 GiB — more than the whole GPU — and it is memory the program never holds. Vx computes the peak from the program's block structure and a declared machine model, at compile time, on a laptop.

Deciding whether a model fits on a card is the decision that sets everything after it: one GPU or two, resident weights or streamed ones, a batch size you can serve or one you cannot. It is usually settled by adding numbers up, and a sum is the wrong quantity.

Why the sum is wrong

A tensor occupies the card between its allocation and its release. Two tensors need room at the same time only if those intervals overlap. So the quantity that has to fit is the peak over the run, and a sum describes a moment the program never has.

For transformer inference the gap between the two is enormous, and it falls along a clean line:

  • Weights are resident. Every layer is read on every token, so all 32 layers' matrices sit on the card from the first token to the last. Lifetime analysis has nothing to offer here — these really are all live at once.
  • Activations are not. Layer 7's attention scores are dead the moment layer 8 starts. There are 32 layers' worth of them in the sum and one layer's worth on the card.

That second line is where the 43 GiB lives. Getting it wrong pushes you toward offloading, which is expensive, and the expense is the point of the whole exercise.

A sum, a peak, and twenty lines

Here is the shape of the problem with the sizes made small enough to read. One resident buffer, and a scratch buffer allocated inside a loop that runs 32 times:

Memory CPU_DRAM {}
Memory HBM {
  within: Memory::CPU_DRAM, capacity: 4 MiB, bandwidth: 1555 GB/s, managed: cached
}
Topology Dev {
  arch: nvptx64,
  memory: Memory::HBM,
  visible: [Memory::HBM],
  transfer Memory::CPU_DRAM -> Memory::HBM : 31.5 GB/s
}

fn main() -> i32 {
  let weights_h = Tensor<f32, [512, 512]>::uninit();
  let mut weights = transfer(weights_h, Memory::HBM);
  for layer in 0..32 {
    let scratch_h = Tensor<f32, [512, 512]>::uninit();
    let scratch = transfer(scratch_h, Memory::HBM);
    spawn on(Topology::Dev) {
      weights[0][0] = weights[0][0] + scratch[0][0];
    }
  }
  print(2);
  return 0;
}

Thirty-three buffers of 1 MiB each are placed into a 4 MiB space. The compiler admits it, and reports what it admitted on:

"resident_sets": [
  {"space": "HBM", "total_bytes": 2097152, "capacity_bytes": 4194304,
   "utilization": 0.5, "tiles": 2, "overcommit": false}
]

Two tiles, 2 MiB, half the space: the resident buffer plus whichever scratch buffer the current iteration holds. Unroll that loop — write the 32 scratch placements out at function scope, changing nothing else — and the same compiler refuses the same program:

Error[E6010]: the working set placed in memory space 'HBM' (33 tiles) sums to 34603008 bytes,
              over its 4194304 byte capacity; place fewer/smaller tiles or declare it `overcommit`

33 MiB against 4 MiB, utilization 8.25. Both verdicts are correct. The unrolled program really does hold 33 buffers at once, because nothing releases them until the function ends.

How the compiler knows

Every lexical scope gets an id when it is entered, so at any point during checking there is a scope chain: the ids of the blocks currently open, outermost first. Each placement records its size, the chain it was placed under, and its position in program order. At the end of a function, for each space:

peak ← 0
for each tile T, in program order:
    live ← Σ { U.bytes : U placed no later than T,
                         and U.scope is a prefix of T.scope }
    peak ← max(peak, live)

The prefix test is the coexistence test. A tile placed in a block that encloses T's block is still open when T is placed; a tile in a sibling block was released when that block closed. The ordering test handles the rest: a tile placed in the enclosing scope after an inner block closed does not coexist with what was inside it, and prefix alone would say it did.

Three properties make this computable, and it needs all three. Placement is in the type, so transfer(t, Memory::HBM) produces a value whose type names the budget it draws on. Spaces declare a capacity, so the budget is a number in the machine model instead of a property of whichever machine the program lands on. And release follows the block structure, so "do these overlap" becomes a question about the syntax tree.

One design decision is worth stating because it looks like a missed optimization. The obvious refinement is to release a tile at its last use rather than at the end of its block, and the machinery for that already exists — it is what the borrow checker runs on. Using it here would be wrong. The runtime frees at block end, so a tile whose last read is early is dead to the borrow checker and still allocated. Accounting at last-use granularity would be finer than what actually happens, and the check would start admitting programs that then run out of memory. The accounting has to model the release discipline the compiler implements, not the tightest one imaginable.

Llama-2-7B, for real

Now the same structure at the real sizes. Llama-2-7B: 32 layers, hidden 4096, FFN intermediate 11008, 32 heads, vocabulary 32000. A 4096-token prefill, batch 1, f16 throughout, with attention scores materialized. The machine is fleet/a100-40.vx, which declares 40 GiB of HBM at 1555 GB/s and a host link at 31.5 GB/s.

The weights go in at function scope, because that is where they live. The per-layer activations go inside the layer loop, because that is where they live:

fn main() -> i32 {
  // Resident for the whole run: embeddings, the KV cache, and one tile per
  // layer standing for that layer's seven weight matrices.
  let embed = transfer(embed_h, Memory::HBM);        // 250 MiB
  let lm_head = transfer(lm_head_h, Memory::HBM);    // 250 MiB
  let mut kv = transfer(kv_h, Memory::HBM);          // 2 GiB
  let w0 = transfer(w0_h, Memory::HBM);              // 386 MiB, x32
  ...

  for layer in 0..32 {
    // Dead at the end of the iteration, every one of them.
    let scores = transfer(scores_h, Memory::HBM);     // 1 GiB
    let qkv = transfer(qkv_h, Memory::HBM);           // 96 MiB
    let ffn = transfer(ffn_h, Memory::HBM);           // 172 MiB
    ...
  }
  return 0;
}

Two layouts of the same tensors, one machine file, one command:

LayoutTilesWorking setUtilizationVerdict
Every layer's activations at function scope22758.93 GiB1.4731E6010, refused
Activations inside the layer loop4115.94 GiB0.3984admitted

Exactly: 63,271,075,840 bytes against 17,112,760,320. The peak breaks down as 12.06 GiB of layer weights, 0.49 GiB of embeddings, 2 GiB of KV cache and 1.39 GiB for one layer's activations. The other 31 layers' activations — 42.99 GiB of them — are the memory that is never there.

Note what the analysis did not do. It did not shrink the weights. All 32 layers of them are in the peak at full size, counted 32 times, because they are genuinely all live. A lifetime analysis that reported anything smaller would be lying. The saving comes entirely from the buffers whose lifetimes really are disjoint, which is the only place it can come from.

What the wrong answer costs

Suppose you believed the 58.93. The model does not fit, so the weights get streamed from host memory as each layer runs. The same machine file prices that, because the host link is a declared edge, and the compiler reports the cost of each transfer it plans:

{"path": ["CPU_DRAM", "HBM"], "bytes": 404750336,
 "derived_cost": 12849217016, "derived_unit": "ps", "cost_source": "link_rate"}

12.85 ms to move one layer's weights across the host link. Thirty-two layers is 411 ms per token, or 2.4 tokens/s. Had those same weights stayed in HBM, reading all of them costs 13.48 GB at 1555 GB/s — 8.7 ms, or 115 tokens/s as a roofline.

So the accounting error is worth roughly 47× in throughput. It is not a rounding error in a capacity plan; it is the difference between a card that serves the model and a card that streams it.

Where the line actually is

A check that always says yes is not a check. Keeping the prefill at 4096 tokens and raising the batch on the same A100-40:

BatchWorking setUtilizationVerdict
115.94 GiB0.3984admitted
839.65 GiB0.9911admitted
943.03 GiB1.0758E6010, refused

Batch 8 fits with 0.9% of the card to spare and batch 9 does not, and both answers arrive from vxc on a laptop. That is the shape of the question a serving deployment actually asks, answered before anything is scheduled.

What it does not do

The analysis is deliberately conservative, and the conservatism runs in one direction: it can refuse a program that would have fit, and it cannot admit one that does not.

  • It stops at the function boundary. The budget is taken per function, so a tile a caller is holding is not counted against a callee's placements. The quantity wanted there is a peak over the call tree, which needs a call graph and a decision about recursion — Vx#444.
  • A loop body is checked once. That matches the runtime, where the release at the end of the body runs every iteration. It also means the analysis says nothing about a loop that accumulates tiles into something outside it.
  • Only some scopes release. if arms and loop bodies were each checked against the emitted IR and opted in. spawn regions, match arms, comptime and unsafe blocks are left conservative — their tiles stay resident to the end of the function. A match arm is probably releasing on the same grounds as an if arm; it stays out until someone reads the IR, because the cost of being wrong is not symmetric.
  • Shapes must be static. A tile whose size is not known at compile time cannot be added to a budget, and the compiler says so with a warning rather than guessing.

Why this is not the usual state of affairs

The comparison worth drawing is not that other toolchains compute this incorrectly. It is that they are not in a position to ask at compile time.

In C, C++ or Rust a heap allocation is not associated with a bounded named space, so there is nothing to compare a lifetime against; capacity is discovered when an allocator returns null. In CUDA, static __shared__ is bounded per kernel rather than composed across a program's scopes, and device global memory has no compile-time budget at all. Frameworks that place tensors on devices learn the element type, the shape and the device at dispatch, so the peak is discovered by the allocator, at run time, on the machine that either has the memory or does not.

Discovering it there is not useless — it is how everyone does capacity planning today. But the failure is asymmetric in an expensive way. Overestimate and you offload, or rent the larger card, and pay for it every token forever. Underestimate and you find out in production. What the three properties buy is that the number arrives before either bill does.
