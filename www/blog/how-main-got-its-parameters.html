How main got its parameters

Aditya Kumar · 25 November 2026

TL;DR — In Vx, main is where a program gets its rights to use the operating system. A library can open a file only when its caller gives it the right to, and at the start only main has the rights. In six months, main went from returning any type, to returning an i32 exit code, to main(root : Root) two days ago, and today to main(root : Root, args : Vec<String>). This post goes through each form, compares it with main in C, C++, Rust, Go, Java, Zig, Pony and Austral, and says what the new form costs: an argument that is not UTF-8 text stops the program before main runs.

The signature of main is the contract between a program and whoever starts it. It says what the program gets and what it gives back. It also decides what each library in the program can do without asking.

What runs before main

A C program does not start at main. The kernel starts it at _start, which the C runtime provides. _start finds argc, argv and the environment on the stack and calls __libc_start_main. That function sets up the C library, calls main, and gives the value that main returns to exit. The hidden complexity of the simplest C program follows each step.

On a machine with an accelerator, the picture splits in two. "Hello, World!" in a heterogeneous system shows a host main that loads the device code, starts it and copies its result back. The device starts at its own _start, with no operating system. In Vx, main is the host side of that picture. A spawn on block is code that runs on a device, and the host program gives it its data. Only the host program talks to the operating system.

So main is the first function that the program writes, and the place where the words of the command line arrive. It is also the place where the program could get its rights to use the operating system, if the language passes them there.

A main whose value nobody read

For two months, the code generator ignored the return of main. It did not evaluate the expression either. fn main() -> i32 { return 42; } exited with 0, and return f() never called f. The main of a test of a for loop was return test_for_loop(), so the loop never ran. The test passed anyway, because the program exited with 0. Issue #210 found it, and named the cost of each fix: about 50 tests relied on the exit code 0, because the test runner counts any other code as a failure.

The fix chose C's rule. main returns an i32, and that value is the exit code of the process. The same commit changed every test main to return i32. Today fn main() -> void gets this error:

`main` must return i32 (the process exit code), found void

An exit code is still not an i32. Linux and macOS keep only its low 8 bits, so return 256 ends the process with status 0, and the shell sees a success. Writing this post found it (#4031). C has the same problem, and Rust's ExitCode holds a u8 for this reason.

What the forms mean for the programmer

A global hides an input. In Rust and Go, any function can read the command line and the environment, so its signature does not show what it reads. To give such a function other words, a Go test sets the global os.Args. A Rust test cannot change the arguments of its process at all. Zig 0.16 removed its globals os.argv and os.environ, and gave main a parameter that holds them (ziglang/zig#30644). The pull request calls the globals "footguns". A later Zig pull request proposed to parse the arguments into a second parameter of main (ziglang/zig#35304). Vx took a similar path this week.

The return value says what failed. In C, main that ends without a return returns 0, and void main() is not standard C. When a compiler accepts it, the C standard leaves the exit code unspecified. Java's main returns void, so a program calls System.exit to fail. Rust lets main return a Result, so ? works in main, and an error exits with code 1. Austral's main returns an ExitCode with two values, success and failure. Vx has C's rule, and the gap of #4031 with it.

Nobody calls main. C lets a program call main. C++ does not: "The function main shall not be used within a program." Vx needed the C++ rule for a new reason, which the section main(root : Root) shows.

What the forms mean for security

Ambient authority. In C, C++, Rust, Go and Java, every function can open any file that the user can open, and connect to any address. The rights come from the process, so every line of code has them. A library that parses JSON can read ~/.ssh/id_rsa and send it away, and nothing in its signature says so. The npm package event-stream got such code in 2018, through a new dependency, flatmap-stream, that tried to steal from the Copay bitcoin wallet. Mark Miller's thesis, Robust Composition, calls this ambient authority. The fix that it argues for is old: the right to do a thing is a value, and only code that holds the value can do the thing (Dennis and Van Horn, 1966). Rust has the cap-std crate for this, beside its standard library. WASI gives a program no files at all, unless the host gives it a folder.

The arguments are input from an attacker. argv is not only the words that a user typed. The program that starts a process chooses every word, the first one too. In PwnKit (CVE-2021-4034), a user started the setuid program pkexec with no words at all, so argc was 0. pkexec read and wrote argv[1], which was the first environment variable, and any local user got root. The bug was 12 years old. Linux now puts an empty string in argv[0] when a program starts another with no words (the patch). So code that reads argv[0] as "the path of the program" trusts a value that an attacker picks.

Capability types in Vx

On 21 November, issue #3750 asked whether a Vx type can be a capability. It said: "Authority is ambient. Any module can import std::fs or std::net and open any file or socket." The design in docs/discussions/capability_types.md gives a capability three rules. Vx already had each one for a type with an invariant: a struct that states a fact about its fields, such as the fact len <= capacity of Vec. A capability states invariant true, a fact that always holds, and gets the same rules:

  • No forging. Only the file of a type with an invariant can build a value of it.
  • No copying. A struct moves when code uses it.
  • No keeping a lent value. A function that gets &Files uses it during the call, and cannot store it.

std now has two rights. Files is the right to open files, and Network is the right to open connections. Folder narrows Files to the files of one folder. File::open takes a &Files, and TcpStream::connect takes a &Network. A library that wants to read a file it was not given cannot build a Files:

fn read_the_keys() -> i32 {
  let files = Files {};
  ...
}
Error[E8014] at forge_files.vx:6:15: this struct literal builds a `Files`.
`Files` has an invariant, so only code in `fs.vx` can build it from its fields

unsafe code can always make a value, because it can read one from any address. Rust has the same rule. So the promise covers code without unsafe, extern and mlir! (MLIR written inline): such code gets only the rights that its caller gives it. Code with any of the three is the trusted code of the program. Two flags of the Vx compiler, vxc, find it. vxc --audit lists each place:

lib/keys.vx:6:15: trusted code: an `unsafe` block

and vxc --no-trusted-code lib refuses it in the package lib, so a new version of the package cannot add trusted code without an error:

Error[E5003] at lib/keys.vx:6:15: `--no-trusted-code lib` refuses trusted code
in the package `lib`, and this is an `unsafe` block

main(root : Root)

The rights have to start somewhere. The design weighed two ways for main to get them: a parameter, as in Austral, or a call such as std::root() that only the file of main can make. A call can run twice, and each call would make new rights. A parameter arrives once, and the signature shows it. So on 23 November main got a parameter:

import core::result;
import std::fs;
import std::root;
import std::string;

extern {
  fn getenv(name : *const i8) -> *const i8;
}

// A function that opens a file says so in its signature: it takes a `&Files`.
fn exists(files : &Files, path : &String) -> bool {
  match File::open(files, path, OpenMode::Read()) {
    Result<File, FileError>::Ok(_file) => {
      return true;
    }
    Result<File, FileError>::Err(_e) => {
      return false;
    }
  }
}

fn main(root : Root) -> i32 {
  let path = unsafe { String::from_c_str(getenv("FILE")) };
  if exists(&root.files, &path) {
    return 0;
  }
  return 1;
}

A program that needs no right keeps fn main() -> i32. The compiler renames the main above to main_with_root, and writes a main that makes the Root in an unsafe block of its own. --audit leaves that block out, because the program did not write it.

The next day, a check of the design found two holes. First, a function could call main(), and each call made a new Root. A test program printed its line 130,727 times, each time with a new Root, until the stack overflowed (#3865). Vx now has C++'s rule:

Error[E5004]: A program cannot call `main` or use it as a value.
Only the runtime starts `main`. A `main` that takes a `Root` would make a new
`Root` at each call

Second, a library could declare its own main(root : Root). Now only a file on the command line of vxc can declare one, and an imported file that declares one gets an error (#3867).

The command line in the Root

The example above reads its path with getenv, in unsafe. A main that took a Root could not take argc and argv as well. So a program with a Root had no safe way to read its arguments (#3973). Three options came up: a field root.args, the parameters main(root, argc, argv), or a function std::env::args(). The parameters still needed unsafe to read a word. Any library could call the function, so it would hide an input, as a global does. The first version of #3975 took root.args, a Vec<String> in the Root.

A review of that version found four problems:

  1. The command line is not a right. Root held the rights to use the operating system, and now it held data too. Pony has the same shape, with env.args beside env.root, so it can work. But then Root means two things.
  2. A program could only borrow the words. Root has an invariant, so code outside root.vx cannot move a field out of it. And String has no clone. So a program could read root.args, but it could not keep a word in its own options.
  3. Bytes that are not UTF-8 changed silently. String::from_c_str replaces such bytes with U+FFFD. So an argument that names a file could name a different file.
  4. The first word is not "the path of the program". The caller chooses it, as PwnKit shows.

main(root : Root, args : Vec<String>)

Now the words are a second parameter, and main owns them. With the same exists, the program needs no unsafe:

fn main(root : Root, args : Vec<String>) -> i32 {
  let mut i = 1;
  while i < args.len() {
    let name = args.get_ref(i);
    if exists(&root.files, name) {
      println!("{} exists", name);
    } else {
      println!("{} is not there", name);
    }
    i = i + 1;
  }
  return 0;
}

vxc exists.vx -- /etc/hosts /no/such/file prints:

/etc/hosts exists
/no/such/file is not there

The compiler writes this main for it:

fn main(argc : i32, argv : *mut *mut i8) -> i32 {
  return main_with_root(unsafe { root_of_the_program() },
                        unsafe { arguments_of_the_program(argc, argv) });
}

Each problem of the review has an answer:

  1. Root holds only rights again.
  2. args is an ordinary Vec<String>. The program can move a word into its options, or pass the whole vector to a parser.
  3. An argument that is not UTF-8 stops the program before main runs. The next section says why.
  4. This answer is in the docs only. args still holds the first word at index 0, as argv does. The Vx book now says that the caller chooses every word. The first word is usually the name or the path of the program, and it can be empty.

fn main(root : Root) still works. Any other second parameter is an error at main:

Error at main_takes_a_root_and_a_number.vx:14:4: A `main` that takes a `Root`
can take one more parameter only: the words of the command line, as a
`Vec<String>`

Vec<String>, UTF-8 and other platforms

A Vx String holds UTF-8 text. The words of a command line do not have to be text:

PlatformWhat a program getsCan a word hold something that is not Unicode?
Linux, macOSAn array of C strings. Each one is bytes that end at a NUL.Yes. Any byte but NUL.
WindowsOne UTF-16 string. The C runtime or the program splits it into words.Yes. An unpaired surrogate.
WASIget-arguments: func() -> list<string>No. The strings are Unicode.

A language has five choices for a word that is not text:

ChoiceWho does itWhat it costs
Give bytesC, Go, ZigEach program decodes the bytes, or forgets to.
Give a type of the platformRust's args_os and OsStringA second string type in each API that takes a path or an argument.
Replace the bad bytes with U+FFFDVx before todayA word can change silently, and name a different file.
Escape the bad bytes, so that they come back unchangedPython 3 (PEP 383)Strings that are not valid Unicode flow through the program.
RefuseRust's std::env::args, and Vx nowThe program cannot get a word that is not UTF-8.

Vx refuses, because a String that silently differs from the input is worse than an error. The message says which word:

argument 2 of the command line is not UTF-8 text
panic: an argument of the command line is not UTF-8 text

The cost is real. On Linux, a file name can be any bytes, so a user can make a file that a Vx program cannot get as an argument. But File::open takes a &String too, so today a Vx program cannot open that file at all. The two limits agree. When Vx needs such files, it needs a path type that holds bytes, as Rust's PathBuf does. Then another form of main can give the words in that type.

The choice also travels well. On WASI, every word is a Unicode string, so a Vec<String> fits it exactly. If Vx runs on Windows one day, a word with an unpaired surrogate will stop the program in the same way. A program that runs on Linux with ordinary arguments gets the same Vec<String> on each platform.

To test the refusal, vxc had to pass the bytes on first. It kept the words after -- as Rust Strings, so it refused a word that was not UTF-8 itself, before the program ran. It keeps them as OsString now.

What is still open

  • The exit code. main returns an i32, and the process keeps 8 bits of it (#4031).
  • The environment. A program reads an environment variable through an extern call of getenv, which is trusted code. The old functions vx_env_args_count and vx_env_arg also still exist behind extern.
  • Processes and native code. std has no function that starts a process, and native code runs only through extern. Each one will take a right when std gets it.
  • A word that is not text. A path type that holds bytes, and a form of main that gives the words in it.
