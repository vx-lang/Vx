Plain loops at the speed of CUDA

Aditya Kumar · 13 November 2026

TL;DR — In Vx, a GPU kernel is a nested pair of structured for loops annotated with across blocks and across lanes inside a spawn on region. Semantically, across is a checked schedule annotation: deleting every across yields a sequential loop nest with the same result, and the frontend rejects races and non-uniform barrier control flow at compile time (E6032). We timed these loops on an NVIDIA A100 against CUDA. A loop scaling a 4096 × 16384 grid ran in 0.343 ms versus 0.388 ms in CUDA. Three kernels from llm.c—GELU, layernorm, and softmax—written as across loops came within 5% of llm.c's fastest CUDA kernels, and softmax was faster. Closing the gap took two source-level primitives (lanes::sum and fast_tanh/fast_exp) and one MLIR lowering change that propagates the static block size into device IR. We also inspected the sm_80 PTX emitted by nvc++ 26.9 for OpenMP, OpenACC, and C++17 stdpar on the same loops. Every timing is from one A100; "How we measured" documents the exact harnesses and caveats.

Most GPU languages bake the hardware's SIMT execution model into the dynamic semantics: you write a single-thread body, index manually with blockIdx and threadIdx, place __syncthreads() by hand, and hope no data race or divergent barrier slips past review. Vx keeps the structured loop nest and treats parallelism as a statically checked schedule annotation. A promise like that only matters to compiler and PL people if the lowered machine code matches hand-tuned CUDA—so we rented an A100 and measured.

Schedules that preserve sequential semantics

In Vx, across blocks, across subgroups, and across lanes(N) attach hardware-mapping metadata to ordinary for loops inside a spawn on(Topology::Device) region. Before lowering to MLIR, the HIR checker discharges three obligations under diagnostic E6032 so that parallel execution agrees with sequential execution:

  • Level nesting and structured exits (src/hir/check/across.rs): blocks loops sit directly inside spawn on, subgroups inside blocks, and lanes inside blocks or subgroups, up to three axes per level. A lane count is a compile-time constant up to 1024, and break, continue, and return cannot escape an across loop.
  • Disjointness via affine mixed-radix forms (src/hir/check/across_proof.rs): Rather than running a general polyhedral solver on arbitrary heap graphs, the checker represents tensor indices as affine forms Σ c_i · v_i + c_0 over loop induction variables and region-uniform values. For every tensor written in an across loop, every conflicting access pair must fix the loop variable in a mixed-radix sense (each coefficient strictly exceeds the maximum sum of lower-order terms), separate by constant remainders (e.g., 2 * j vs 2 * j + 1), or be guarded by if v == c. Shared writes require explicit effect contracts such as ensures atomic(t).
  • Uniformity and barrier convergence (src/hir/check/across_lanes.rs): Each across lanes loop ends with an implicit block barrier. Code in a block body outside lane loops that writes memory or mutates outer state runs on lane 0 only; the checker tracks uniform and lane0-defined bindings and refuses any lane loop or enclosing branch whose condition depends on non-uniform or lane-0-private values.

Removing every across modifier leaves an ordinary sequential loop nest with the same denotational meaning (up to explicit atomic interleavings or unordered reductions), and the compiler emits a host CPU copy from the same IR when no GPU is present.

One loop: why knowing the block size matters

Here is the first across example from the Vx book, scaled to a 4096 × 16384 grid. Each block owns a row and 256 lanes stride across its 16,384 columns:

spawn on(Topology::Device) {
  for y in 0..4096 across blocks {
    for x in 0..16384 across lanes(256) {
      grid[y][x] = grid[y][x] * 2.0 + (y as f32);
    }
  }
}

The idiomatic CUDA equivalent maps one block per row and steps each thread by blockDim.x:

__global__ void scale_rows(float *grid) {
  int y = blockIdx.x;
  for (int x = threadIdx.x; x < COLS; x += blockDim.x) {
    size_t i = (size_t)y * COLS + x;
    grid[i] = grid[i] * 2.0f + (float)y;
  }
}
// scale_rows<<<4096, 256>>>(grid);

The kernel reads and writes 512 MiB, so it is purely memory-bound. Vx ran 12% faster because the launch configuration is part of the source syntax rather than an opaque runtime parameter at the <<<...>>> call site. In the CUDA version, nvcc must emit a runtime read of %ntid.x (blockDim.x) and maintain an induction step that is unknown at compile time. Because Vx fixes the block width at 256 in the across clause, the device lowering folds the block dimension to a constant, letting LLVM unroll 4 elements per loop iteration at fixed byte offsets with fewer address-calculation instructions. A CUDA programmer who hardcodes 256 in place of blockDim.x gives the compiler the same information; we did not time that variant.

Three kernels from llm.c

A bandwidth-bound scaling loop is a modest test. llm.c provides a progressively tuned suite of GPT-2 CUDA kernels along with a timing harness. We ported three of them—GELU, layernorm, and softmax—into Vx at llm.c's shapes. Here is llm.c's baseline GELU kernel:

__global__ void gelu_forward_kernel1(floatX* out, const floatX* inp, int N) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < N) {
        float xi = inp[i];
        float cube = 0.044715f * xi * xi * xi;
        out[i] = 0.5f * xi * (1.0f + tanhf(GELU_SCALING_FACTOR * (xi + cube)));
    }
}

And the Vx version:

pub fn gelu_forward(out : &mut Tensor<f32, [?], Memory::HBM>, inp : &Tensor<f32, [?], Memory::HBM>, n : i32) -> void {
  spawn on(Topology::Device) {
    for b in 0..(n + 255) / 256 across blocks {
      for l in 0..256 across lanes {
        let i = b * 256 + l;
        if i < n {
          let x = inp[i];
          let cube = 0.044715 * x * x * x;
          out[i] = 0.5 * x * (1.0 + (0.7978846 * (x + cube)).fast_tanh());
        }
      }
    }
  }
  return;
}

Notice two properties that matter for static verification. First, the loop bound (n + 255) / 256 combined with b * 256 + l is proven non-wrapping by across_proof.rs without needing a runtime overflow guard at launch (whereas an unbounded 0..n with i32 indexing emits a host guard before dispatch). Second, gelu_forward is an ordinary public function: the borrow checker verifies memory access and the same source executes sequentially on the CPU when no GPU is attached.

What it took: primitives and one MLIR lowering fix

Our initial Vx ports were roughly 2× slower. Closing the gap required two changes in the source programs and one compiler optimization.

1. Structured collective reductions (lanes::sum, lanes::max). In layernorm and softmax, each lane computes partial accumulators across a row before collapsing them into a scalar. Our first versions wrote that reduction as a plain sequential loop after the lane loop—which under Vx's barrier semantics runs on lane 0 alone, serializing a 256-way reduction. llm.c uses a warp-shuffle and shared-memory tree, and Vx provides lanes::sum and lanes::max as compiler-recognized collectives with a fixed two-level reduction order (shfl.sync.bfly.b32 / shfl.sync.down across 32-lane warps, followed by a cross-warp step). Because the tree is deterministic, every lane receives identical bits and the result is typed as uniform. Replacing the scalar loop with lanes::sum cut layernorm from 0.088 ms to 0.043 ms, and together with fast_exp cut softmax from 0.130 ms to 0.050 ms.

2. Separating IEEE-exact math from fast device approximations (fast_tanh, fast_exp). Vx's default tanh and exp are specified to return the exact nearest f32 on both CPU and GPU. To guarantee bit-identical rounding, the standard implementation promotes internally to f64, which hits a hardware throughput wall on GPUs where f64 issue rate is a fraction of f32. Rather than exposing a global -ffast-math flag that silently alters floating-point semantics across an entire compilation unit, Vx makes the precision trade-off explicit at the call site via fast_tanh and fast_exp, which lower to short f32 GPU sequences like CUDA's intrinsics. Switching GELU to fast_tanh dropped its runtime from 0.060 ms to 0.047 ms (see Exact and fast math).

3. Propagating the static block size and thread upper bound in MLIR (#3354). Every kernel lowered by Vx already carries its static thread count in vx.launch_block, and the ABI guarantees the kernel is launched with exactly that block size. However, the MLIR-to-LLVM device lowering (ConvertVxToStandardPass in src/dialect/VxLowering.cpp) previously stepped each across lanes(W) loop by min(W, gpu.block_dim). Even when W == 256 matched the 256-thread block—as in GELU, where every lane executes exactly one iteration—LLVM saw an opaque gpu.block_dim, could not fold the trip count to 1, preserved the loop backedge, and strength-reduced the index into a separate 64-bit byte offset, costing two extra instructions per load and store.

In #3354, when vx.launch_block is a compile-time integer, the GPU device clone replaces gpu.block_dim with that constant and attaches it as the upper-bound attribute on gpu.thread_id (without emitting nvvm.maxntid for blocks of 256 threads or fewer, since .maxntid alters ptxas register allocation). On the CPU fallback clone, gpu.thread_id and gpu.block_dim still fold to 0 and 1. With that single change, LLVM proves single-trip lane loops dead, eliminates the bounds check against 256, and computes element addresses directly. Every benchmarked kernel sped up by 4% to 10% with identical output bits:

Comparison with OpenMP, OpenACC, and C++ stdpar

C and C++ programmers already have three standard ways to annotate plain loops or algorithms for a GPU: OpenMP target offload, OpenACC directives, and C++17 parallel algorithms (std::for_each(std::execution::par_unseq, ...), or stdpar). We wrote the scaling loop, GELU, and layernorm in all three and compiled them with nvc++ 26.9 (NVIDIA HPC SDK) at -O3 targeting sm_80. We did not execute these binaries; instead, we inspected the emitted PTX to compare the generated instruction shapes.

The 4096 × 16384 scaling loop. The conventional pragma style uses collapse(2):

#pragma omp target teams distribute parallel for collapse(2)
for (int y = 0; y < ROWS; y++)
  for (int x = 0; x < COLS; x++)
    grid[(long)y * COLS + x] = grid[(long)y * COLS + x] * 2.0f + (float)y;

With collapse(2), both OpenMP and OpenACC flatten the nest into a 67-million-trip 1D loop. On every iteration, the PTX reconstructs y and x from the linear index via 64-bit shifts and masks—roughly 15 instructions of index arithmetic per load-store pair—and marks the loop un-unrollable. If we instead write the two-level decomposition explicitly (rows on blocks/gangs, columns on threads/vectors), the generated PTX diverges sharply across compilers:

Rows on blocks, columns on threadsGenerated PTX (sm_80)
Vx4 elements per loop iteration at fixed offsets, with no per-element bounds test
OpenACC, gang and vector_length(256)16 elements per iteration at fixed offsets, plus a 3-instruction bounds test per element
OpenMP, teams distribute + parallel for1,188 instructions, a call into the OpenMP device runtime, a local-memory stack, and a shared-memory state machine
stdpar, std::for_each over flat index2 elements per thread at fixed offsets (the underlying CUB dispatch fixes 256 threads)
CUDA, using blockDim.x1 element per iteration with 4 instructions to form the 64-bit address because blockDim.x is opaque

OpenMP's 1,188-instruction kernel reflects its fork-join execution model: nesting parallel for inside teams distribute emits a dynamic parallel region per team where a single thread initializes and wakes worker threads via a shared-memory state machine.

GELU. Vx, OpenMP, OpenACC, and stdpar all emit the same instruction sequence for tanh: ex2.approx, rcp.approx, and a polynomial evaluation. Only nvcc --use_fast_math improves on it by lowering directly to the single hardware instruction tanh.approx.f32, which Vx's fast_tanh does not yet emit (#3359).

Layernorm. Each row requires two reductions. Vx lowers lanes::sum to register-level warp shuffles, producing a self-contained 168-instruction kernel with zero runtime calls. In C++ with nvc++:

  • OpenACC (loop vector reduction(+: s) inside a gang loop) lowers to a shared-memory reduction tree in 188 instructions and 12 barriers—close to Vx.
  • OpenMP (parallel for reduction(+: s) inside teams distribute) expands to 3,657 instructions and accumulates per-thread partials into shared memory using atomic adds, serializing threads within each block.
  • stdpar forbids nested parallel algorithms inside a device kernel. The natural formulation assigns one thread per row to reduce 768 elements sequentially—launching only 8,192 threads on a GPU capable of 221,184 resident threads, with neighboring threads striding 3 KB apart (uncoalesced global loads). The alternative, dispatching std::reduce per row, incurs 16,384 separate kernel launches.

Soundness on racy loops. Pragmas are unchecked hints. When we fed nvc++ a loop with a cross-iteration write collision—out[i / 2] = inp[i]—under both OpenACC and OpenMP, it compiled silently into a data race. Vx's affine proof rejects the same loop at compile time because i / 2 does not fix the loop variable:

Error[E6032]: two passes of this block loop may write the same element of `out`: an index of the write must fix `b`

A disciplined C++ programmer using OpenACC can obtain code nearly as clean as Vx by picking the right pragma nest and verifying non-interference by hand. Vx's contribution is making that well-structured, two-level form the only form, keeping reductions in lanes::, and proving disjointness and barrier convergence statically.

How we measured

Microbenchmark methodology shapes GPU numbers, so here are the exact conditions and limits:

  • Hardware and toolchain: One NVIDIA A100-SXM4-80GB, CUDA 12.8, driver 595.91. Each kernel ran at one fixed problem size on an otherwise idle GPU.
  • Single-launch timing: With VX_TIME_KERNEL=1, Vx brackets each individual launch with CUDA events. Tables report the median of 50 launches (10 launches for the 4096 × 16384 scaling loop). The baseline CUDA scaling kernel was timed with the identical single-launch event harness.
  • llm.c's own harness: llm.c times a back-to-back stream of launches and divides by the count. On this A100, back-to-back averaging shaves roughly 4 µs of launch overhead relative to single-launch event timing, which biases the layernorm and softmax rows in llm.c's favor. For GELU, we timed llm.c's kernel with the same single-launch harness as Vx (0.046 ms).
  • 1000 back-to-back launches: To control for harness differences on GELU, we loaded Vx's generated GPU code and nvcc's GPU code into a single binary and executed each 1000 times consecutively across 7 trials. Variance was under 1%, with Vx 2% slower.
  • Fast math: llm.c baselines were compiled without --use_fast_math unless noted. Enabling --use_fast_math sped up llm.c by up to 9%. Vx restricts fast approximations to explicit fast_* calls.
  • L2 cache residency: Layernorm's input tensor is 25 MB, which fits inside the A100's 40 MB L2 cache; this favors implementations like our Vx port that read the row three times.

What is left

  • Half-precision math intrinsics: across loops do not yet support tanh or fast_tanh on f16 or bf16 (#3353). llm.c's highest-throughput kernels run in bf16.
  • Other GPU architectures: All timings are from an A100. GPUs with lower f64 throughput (such as an NVIDIA L4) will exhibit a much steeper penalty when using exact tanh/exp instead of fast_*.
  • Richer kernels: Matrix multiplications in llm.c dispatch to cuBLAS, and fused attention kernels exercise warp-group scheduling and asynchronous shared-memory copies beyond simple across lanes loops.
