What writing core taught the compiler

Aditya Kumar · 21 September 2026

TL;DR — A week ago, stdlib/core/ did not exist. Now it holds eight modules (cmp, option, result, num, ops, iter, clone, and default) plus a reproducible random-number library (std::rand), shipped as part of Vx v0.0.2. Every line is written in pure Vx, without a single extern in sight. Writing it was the ultimate stress test for our compiler: a standard library is the first program that forces every language feature to work together simultaneously. Here is what we built, how we tested it, and the compiler bugs that writing it uncovered.

Writing a compiler frontend is deceptive. Your unit tests are small, tidy, and well-behaved: they test one feature in isolation, like whether an enum can match or a generic can monomorphize. Then you sit down to write its standard library, and the illusion shatters.

A standard library cannot test features in isolation. It forces generic traits with default method implementations to return enums containing inline hardware intrinsics, all composed inside lazy iterator adapters. In one week, building Vx's core library surfaced compiler gaps that had hidden in plain sight across our parser, type checker, and code generators.

The architectural split: Why core matters

Previously, Vx had a single 1,358-line std where disparate abstraction layers were tangled together: Option<T> lived beside TcpStream, and Result<i32, i32> was backed by six foreign C symbols in a Rust crate. Following Rust's proven architectural tiered model, we split the library into clean layers:

  • core: Pure language fundamentals. No operating system dependency, no dynamic heap allocator, no thread scheduler, and zero libc calls.
  • alloc: Dynamic data structures that require an allocator (like Vec, String, and HashMap).
  • std: The full operating system interface (filesystem, networking, processes, and wall-clock time).

The golden rule: Zero extern calls

Every module in core obeys one non-negotiable rule: no extern blocks allowed.

Why? Because Vx is a heterogeneous systems programming language. A function written in core must run anywhere: on an x86 host CPU, inside an accelerator region with spawn on(Topology::GPU[0]), on the Apple Neural Engine, or on a bare-metal microcontroller like an ARM Cortex-M7 with no C runtime. If Option::unwrap or a bitwise count called an external C symbol, executing that code on an accelerator would fail immediately.

Where Rust's core reaches for magic compiler intrinsics (core::intrinsics), Vx reaches for mlir!: an inline MLIR block that our compiler pipeline lowers natively to hardware instructions. A population count (bit count) is expressed directly in MLIR, right where the library author can see and audit it:

impl u64 {
  fn count_ones(self : u64) -> u64 {
    return mlir!( inputs : (%a = self : i64), returns : u64, dialects : ["math"]) {
      %r = math.ctpop %a : i64
      macro.yield %r : i64
    };
  }
}

Because every backend in `vxc` understands the MLIR math dialect, this single implementation compiles portably to native LLVM IR on the CPU, NVVM/PTX on NVIDIA GPUs, and hardware-specific instructions across all targets, without a single byte of foreign runtime overhead.

The trait tower for comparisons works because trait default method bodies landed in the compiler at the same time. By defining just eq and cmp, a type gets ten comparison methods for free:

import core::cmp;

fn main() -> i32 {
  let a : i32 = 3;
  let b : i32 = 9;
  print(a.max(b));
  print(b.clamp(0, 5));
  if a.cmp(&b).then(b.cmp(&a)).is_lt() {
    print(1);
  }
  return 0;
}

Likewise, for loops now seamlessly consume anything that implements the Iterator trait, including chained adaptors:

import core::iter;

fn main() -> i32 {
  let mut evens = filter(range(0i64, 10i64), | x : i64 | x % 2i64 == 0i64);
  for x in evens {
    print(x);
  }
  return 0;
}

Random numbers that can replay anywhere

Alongside core, we rebuilt std::rand. Our old generator was SplitMix64 hidden behind a set of foreign C runtime symbols sharing a single global counter. In a concurrent or multi-device environment, two threads populating tensors would interleave their draws unpredictably, making deterministic debugging impossible.

The new std::rand implements the modern xoshiro256** algorithm in pure Vx, keeping the entire generator state inside a local Rng struct. Two generator instances seeded with the same value produce identical pseudo-random streams anywhere in the world:

import std::rand;

fn main() -> i32 {
  let mut r = Rng::seeded(7);
  print(r.next_f32());               // uniform in [0, 1)
  print(r.range_i64(-5, 5));         // unbiased, by rejection sampling
  print(r.normal_around(0.0, 0.02)); // polar Box-Muller transform
  let mut again = Rng::seeded(7);
  print(again.next_f32());           // exactly identical first draw
  return 0;
}

Determinism is essential for heterogeneous systems. Differential testing compares two execution paths—such as an optimized CUDA kernel on an A100 versus a CPU reference implementation—on the exact same input data. If random inputs vary across runs or backends, differential correctness is impossible to assert.

Additionally, generating normal (Gaussian) distributions natively is critical for deep learning workloads: real neural network weights and activations cluster around zero. Testing half-precision (f16/bf16) kernels with uniform noise fails to exercise the tail underflow and overflow conditions that cause silent training divergence.

What the compiler learned (The bugs that dogfooding found)

Writing standard library code was the ultimate crucible for the compiler. Every single module was written by first debugging whatever compiler bug blocked it. When generics, traits, macros, enums, and inline MLIR collided in the same source file, the compiler's hidden seams burst open.

Some were straightforward feature omissions: the language was missing basic bitwise operators (%, &, |, ^, <<, >>); trait methods could not declare generic type parameters of their own; and trait default bodies were accidentally dropped when an impl block was instantiated. But the more fascinating bugs were deep architectural assumptions that had remained unnoticed until now.

1. The linter with amnesia (The nested call bug)

The moment we imported std::rand, the compiler flooded the console with fourteen bogus warnings claiming function parameters were unused—even though they were clearly read:

struct Counter {
  n : f64,
}

impl Counter {
  fn next(self : &mut Counter) -> f64 {
    self.n = self.n + 1.0;
    return self.n;
  }

  // Used to trigger: unused parameter 'lo', unused parameter 'hi'
  fn range(self : &mut Counter, lo : f64, hi : f64) -> f64 {
    return lo + (hi - lo) * self.next();
  }
}

Why did this happen? The semantic analyzer maintained a single, global HashSet of used names for the entire compilation session and cleared it after checking each function. However, when the type checker encountered a call inside range (like self.next()), it recursively checked the callee's body first. When the callee finished, it cleared the global set! As a result, all names read in the caller before the call were erased from memory, causing the compiler to accuse the caller of having unused parameters.

The bug appeared intermittent because only the first caller to invoke a callee triggered the nested check; subsequent callers found the callee already verified. Scoping the used-name analysis per function frame solved the issue permanently.

2. The non-deterministic dice roll (Hash map dispatch)

Consider a scalar implementing two distinct traits that both provide a method with the same name:

trait Loud {
  fn describe(self : &i64) -> i32;
}

trait Quiet {
  fn describe(self : &i64) -> i32;
}

impl Loud for i64 {
  fn describe(self : &i64) -> i32 {
    return 1;
  }
}

impl Quiet for i64 {
  fn describe(self : &i64) -> i32 {
    return 2;
  }
}

When compiling a test program that invoked x.describe() across multiple runs, the binary printed: 1, 1, and then 2! Method resolution was iterating through an unsorted Rust HashMap of trait implementations and blindly selecting the first match that matched the method name.

To eliminate this non-determinism, we established clear precedence rules: inherent methods always take priority over trait methods, and ambiguous calls between multiple conflicting trait implementations are rejected at compile time with a clear diagnostic:

Error[E3035]: Method 'describe' on 'i64' is defined by more than one impl (Loud, Quiet);
a call cannot choose between them

3. The invisible static methods

When writing core::default and core::clone, we ran into a wall: calling Default::default() or T::default() refused to compile. The method lookup routine for static calls (Type::method()) was only searching inherent impl blocks, completely ignoring traits. Furthermore, it only looked up types by name across structs and enums, meaning any static method on a primitive scalar (like i32::min_value()) was rejected as non-existent.

Fixing static method lookup to traverse both inherent and trait tables across all types unblocked core::default and core::clone, allowing idioms like Default::default() to work as expected.

4. The 64-bit sign flip

In core::num, integer literals larger than i64::MAX (such as 0x8000_0000_0000_0000u64) crashed our default bytecode lowering path and printed as negative numbers on our legacy codegen path. Because negated literals were being typed purely by their lexical spelling rather than context, an expression like -2.0 * ln(x) with x : f64 failed type checking, even though 2.0 * ln(x) compiled without issue. Context-sensitive numeric typing resolved the issue across both compilers.

Testing by sabotage: Mutation testing in action

Our rule for compiler verification is straightforward: never trust a test you have not watched fail. Seeing a green checkmark only proves the test passed; it does not prove the test was capable of catching a bug.

To verify std::rand, we created 29 distinct, single-edit mutations in rand.vx (altering a shift distance, flipping an addition to subtraction, swapping a state word update) and ran each mutation against our integration test fixture. Every single mutation was expected to trigger a specific, predicted failure.

The first round exposed a major blind spot: one mutation failed to break anything! The rejection-sampling loop inside range_i64 was never being entered because the test bounds never forced a rejection. The test was 100% green, yet the core algorithmic branch was completely untested. Adjusting the bounds to sit just above half the range forced the rejection loop to execute, requiring seven draws to produce the value and making the test sound.

A similar mutation check on Option::clone uncovered a compiler bug: removing the None branch from a match expression compiled cleanly without an exhaustiveness error! The compiled function simply fell off its end at runtime, returning an invalid memory slot. Mutation testing caught the missing exhaustiveness check before it could escape into production.

What comes next

With stdlib/core/ established, our roadmap moves to the next layer:

  • Trait-Qualified Name Mangling (core::convert): Currently, implementing From<i32> for i64 and From<u8> for i64 generates colliding symbol names (i64$from). Extending name mangling to encode the originating trait will unlock the full From/Into conversion suite.
  • Automatic Destructors (Drop): Implementing the Drop trait for deterministic, RAII-based cleanup of heap-allocated structures without a garbage collector.
  • The alloc Layer: Bringing first-class Vec, String, and HashMap abstractions onto the new core foundation.

All eight core modules and std::rand are now live in stdlib/core and shipped in Vx v0.0.2. You can browse every signature in the Standard Library Reference, read the Core Library Implementation Plan, or install Vx today to try it yourself.
