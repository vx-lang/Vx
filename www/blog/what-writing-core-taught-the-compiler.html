What writing core taught the compiler

Aditya Kumar · 21 September 2026

TL;DR — a week ago stdlib/core/ did not exist. Now it holds cmp, option, result, num, ops and iter, about 1,400 lines, with std::rand beside them and clone and default in review. Every line is Vx, and none of it declares an extern. Writing it kept finding compiler bugs, because a standard library is the first program that uses every feature at once.

The standard library was one 1,358-line std with the layers Rust keeps apart mixed together: Option<T> next to TcpStream, and Result<i32, i32> standing on six C symbols in a Rust crate. The plan was to rebuild the bottom layer as core, with Rust's core as the checklist and its public API, module by module, as the definition of done.

One rule

core contains no extern block. What Rust's core gets from core::intrinsics, Vx's gets from mlir!, an inline block of MLIR that every backend lowers. So a bit count is the hardware instruction, written where a library author can see it:

impl u64 {
  fn count_ones(self : u64) -> u64 {
    return mlir!( inputs : (%a = self : i64), returns : u64, dialects : ["math"]) {
      %r = math.ctpop %a : i64
      macro.yield %r : i64
    };
  }
}

The rule is what lets a core module run inside a spawn on(..) region on a device that has no libc. It is also what makes a module portable across the two code generators the compiler currently has, since neither has to know a runtime symbol the other does not.

The trait tower is the shape Rust has, and it works because default method bodies landed the same week. A type writes eq and cmp and gets the other ten:

import core::cmp;

fn main() -> i32 {
  let a : i32 = 3;
  let b : i32 = 9;
  print(a.max(b));
  print(b.clamp(0, 5));
  if a.cmp(&b).then(b.cmp(&a)).is_lt() {
    print(1);
  }
  return 0;
}

And for drives anything with a next, adaptors included:

import core::iter;

fn main() -> i32 {
  let mut evens = filter(range(0i64, 10i64), | x : i64 | x % 2i64 == 0i64);
  for x in evens {
    print(x);
  }
  return 0;
}

Random numbers that replay

std::rand replaced a runtime call. The old generator was a SplitMix64 behind six C symbols with one global counter, which meant two threads filling two tensors interleaved their draws and neither tensor could be replayed on its own. The new one is xoshiro256** with the state in the struct, so two Rng values are two streams:

import std::rand;

fn main() -> i32 {
  let mut r = Rng::seeded(7);
  print(r.next_f32());               // uniform in [0, 1)
  print(r.range_i64(-5, 5));         // unbiased, by rejection
  print(r.normal_around(0.0, 0.02)); // the polar method
  let mut again = Rng::seeded(7);
  print(again.next_f32());           // the same first draw
  return 0;
}

Determinism is the property that matters here. A differential test compares two execution paths on the same inputs, which is only meaningful if the inputs can be produced twice, on every platform. The draws are integer arithmetic and the conversions to float are IEEE, so they are. The normal distribution exists because uniform is the wrong shape for anything that stands in for model data: weights and activations are roughly Gaussian, and a uniform fill exercises a range of magnitudes real data never has, which matters most in f16, where the interesting failures are overflow and underflow at the tails.

What the compiler learned

This is the larger share of the week. Each module was written by first fixing whatever stopped it, and the pattern held from the first one to the last: the library is the first program that combines generics, traits, macros, enums and inline MLIR in one file, and the seams show.

Some were plain gaps. The integer operators %, &, |, ^, << and >> did not exist. A trait method could not have type parameters of its own. A trait's default body was dropped when an impl inherited it. A negated literal was typed by its spelling alone, so -2.0 * ln(x) with x : f64 was a type error, though 2.0 * ln(x) was fine. A u64 above i64::MAX crashed one code generator, and printed as a negative number on the other.

Others had been wrong for a while without anyone standing where they could see them.

The warnings that forgot. Importing std::rand printed fourteen warnings that its parameters were unused. They were used. The checker kept one set of used names for the whole compilation and cleared it at the end of every function, and a callee is checked from inside its caller's body, so the first call a body made wiped the names read before it:

struct Counter {
  n : f64,
}

impl Counter {
  fn next(self : &mut Counter) -> f64 {
    self.n = self.n + 1.0;
    return self.n;
  }

  // Used to report: unused parameter 'lo', unused parameter 'hi'.
  fn range(self : &mut Counter, lo : f64, hi : f64) -> f64 {
    return lo + (hi - lo) * self.next();
  }
}

Only the first caller of a given callee was affected, because the second found it already checked and nothing nested. That is what made it look arbitrary for as long as it did.

The method that changed between runs. Two traits each define describe for i64:

trait Loud {
  fn describe(self : &i64) -> i32;
}

trait Quiet {
  fn describe(self : &i64) -> i32;
}

impl Loud for i64 {
  fn describe(self : &i64) -> i32 {
    return 1;
  }
}

impl Quiet for i64 {
  fn describe(self : &i64) -> i32 {
    return 2;
  }
}

Three runs of the same compiler on a program that called x.describe() printed 1, 1, 2. Dispatch walked a hash map of impl blocks and took the first match. The fix, in review as this is written, chooses the way Rust does: an inherent method over a trait's, and two traits' refused with a diagnostic that names both, since a call has no spelling to say which it means:

Error[E3035]: Method 'describe' on 'i64' is defined by more than one impl (Loud, Quiet);
a call cannot choose between them

The static method that did not exist. Type::method() searched the inherent impl blocks only, so a trait's static method was refused, which is every Default::default() and every From::from(). It also matched the target by name over structs and enums, so any static method on a scalar was refused too, trait or not. core::default waited on that one, and it is in review now.

How the numbers are checked

Every module has a fixture that prints values, and the values are written out rather than checked for looking right. For rand they come from a separate implementation of xoshiro256** and SplitMix64 written from the published algorithms, so a wrong constant, a wrong shift or a state word updated out of order changes them. For num every operand is above the signed range of its width, so a body that read a sign gives a different answer rather than the same one by luck.

Then each assertion is checked by breaking the thing it names. Twenty-nine single-edit mutations of rand.vx, each run against its fixture, each noticed by a specific part of the expected line. The first round found one that noticed nothing: no bound in the test ever rejected a draw, so the rejection loop in below, the part of the function the comment is about, was never entered. A bound just above half the range fixed that. It now takes seven draws to answer.

The same round on core::clone found a compiler bug instead of a test gap. Deleting the None arm of Option's clone was meant to be refused, and was not: the match compiled, the function fell off its end, and the fixture read back a wrong Some. That is filed, and it is the reason the code generator has to synthesize a default return at all.

What is not done

core::convert is designed as one From impl per pair of widths, and those collide: a method's mangled name carries the target type and the method and nothing of the trait, so impl From<i32> for i64 and impl From<u8> for i64 are both i64$from. The call is refused today instead of reaching one of them silently, which is right, and leaves the module waiting on mangling that carries the trait. mem, ptr, hint, marker and panic are unstarted and mostly small. Drop is the large one, and everything that owns something waits on it.

And the plan's own scoreboard, the parity matrix that every PR was supposed to update, still says none of this exists. That is next.

The modules are in stdlib/core, every signature is in the standard library reference, and the plan with its parity matrix is core_library.md. Vx is Apache 2.0 with the LLVM exception — install it.
