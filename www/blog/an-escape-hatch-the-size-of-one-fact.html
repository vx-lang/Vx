An escape hatch the size of one fact

Aditya Kumar · 17 November 2026

TL;DR — A GPU scatter kernel that writes to y[idx[b]] cannot be proved race-free by any static analysis, because the elements of idx are runtime data. Vx's Distinct<..> type lets the programmer supply exactly that one missing invariant—injectivity, idx[a] == idx[b] ⇒ a == b—either via a runtime check on the host or an isolated unsafe construction. Unlike C loop pragmas (ivdep, assume_safety, omp) that disable dependence checking across an entire loop, Distinct narrows the trust boundary to one immutable 1D tensor while leaving every other race and borrow check active. C's restrict cannot express value-level distinctness at all.

In a mixture-of-experts layer, a router assigns each token to a subset of experts. Each expert runs its compute and scatters results back into the rows of the tokens it owns. That scatter is a single line of code, and the Vx race checker refused to compile it.

The kernel that did not compile

Here is the scatter kernel in its natural form: block b accumulates row b of x into token row idx[b] of y:

fn add_to_rows(y : &mut Tensor<f32, [?, ?], Memory::HBM>, idx : &Tensor<i32, [?], Memory::HBM>,
               x : &Tensor<f32, [?, ?], Memory::HBM>) -> void {
  spawn on(Topology::Device) {
    for b in 0..idx.len() across blocks {
      for l in 0..64 across lanes(64) {
        y[idx[b]][l] += x[b][l];
      }
    }
  }
  return;
}
Error[E6032] at add_to_rows.vx:5:9: two passes of this block loop may write the same element of `y`: an index of the write must fix `b`

Because the iterations of an across blocks loop execute concurrently in an unspecified order, Vx requires a static proof that no two distinct iterations write to the same memory location (or that every access to that tensor is atomic). Here, if idx contained row 7 twice, two blocks would perform a non-atomic read-modify-write on y[7][l] simultaneously and lose an update. The compiler is right to reject it.

Yet the domain invariant holds: the router sends each token to a given expert at most once, so within one expert's dispatch list idx has no duplicates. Earlier, the Qwen MoE implementation in Vx (vx-lang/qwen-vx#16) had to work around E6032 by copying expert IDs back to the host per token chunk, sorting the tokens by expert on the CPU, and padding each expert to a multiple of 16 rows so block b wrote contiguous rows 16b through 16b + 15—a linear index that trivially fixes b. That workaround imposed a host-device synchronization wait on every layer: 48 waits per chunk on the 30B model.

What a static race checker proves

In polyhedral compilation, loop-level race checking and dependence analysis are formulated over iteration domains. Each dynamic instance of a loop nest is an integer tuple constrained by a system of linear inequalities:

{ (b, l) : 0 <= b < n, 0 <= l < 64 }

Each array reference defines an access relation mapping iteration points to element coordinates. For a direct write y[b][l], the map is the identity (b, l) → (b, l). Disjointness across b asks whether the existential query is satisfiable:

exists (b1, l1), (b2, l2) in the domain:  b1 != b2  and  (b1, l1) == (b2, l2)

When loop bounds and subscript expressions are affine, this query lives in Presburger arithmetic, which is decidable. Frameworks such as isl, Pluto, LLVM's Polly, and MLIR's affine/Presburger library answer queries of this shape to certify parallelization, tiling, and loop fusion without altering sequential semantics.

Vx's current frontend checker (src/hir/check/across_proof.rs) proves a structural subset of these queries with pattern rules over mixed-radix affine forms, without an ILP solver. An access fixes a loop variable b when its subscript terms form a mixed-radix representation—for example, b * 64 + l with 0 <= l < 64, where each coefficient strictly bounds the maximum sum of lower-order terms. An open design (#3561) plans to replace these pattern rules with explicit iteration domains and one query to Z3.

Where static analysis stops

Affine dependence models are complete within their fragment, and the boundaries of that fragment are well known:

  • Non-linear expressions. Subscripts and bounds must be affine combinations of loop variables and region-uniform constants. Products like i * j, or b * n where n is read from memory, fall outside Presburger arithmetic.
  • Data-dependent control flow. A branch condition loaded from memory cannot be encoded as an affine constraint on the iteration vector, forcing a sound checker to approximate both branches conservatively.
  • Aliasing across distinct names. Polyhedral models typically assume disjoint array spaces per symbol. In languages with raw pointers like C, two parameters may alias the same backing buffer unless proved disjoint or annotated with restrict.
  • Solver complexity. These existential queries are integer linear programs, and integer linear programming is NP-complete, so a production compiler must bound solver time.
  • Indirect subscripting (y[idx[b]]). An access through a runtime array introduces a data-dependent mapping from b to row indices. Because the array's values do not exist at compile time, any sound static analyzer must assume idx[b1] == idx[b2] is possible for b1 != b2 and reject parallelization.

No better solver removes that fifth limit, because the invariant is absent from the kernel's source code.

Compiler research offers two classic approaches. An inspector-executor scans idx at runtime immediately before the loop and dispatches to either a parallel or sequential executor, paying an O(n) inspection pass on every launch. The sparse polyhedral framework models idx as an uninterpreted function symbol and augments the dependence test with domain-specific axioms such as injectivity (Strout, Hall, and Olschanowsky, Proceedings of the IEEE, 2018), allowing the compiler to simplify dependence predicates or emit cheaper inspectors (Mohammadi et al., PLDI 2019). The framework still requires a trusted source for those axioms.

Distinct: reifying injectivity in the type system

Vx reifies that missing axiom as a type constructor in the function signature. Changing one parameter type in add_to_rows makes the kernel compile:

idx : &Distinct<Tensor<i32, [?], Memory::HBM>>

A caller constructs a Distinct value in one of two ways. In safe code, Distinct::check sorts a copy of the tensor on the CPU to verify uniqueness, returning Option::None if any duplicate exists:

match Distinct::check(tokens) {
  Option<Distinct<Tensor<i32, [?]>>>::Some(rows) => {
    let on_gpu = transfer(rows, Memory::HBM);
    add_to_rows(&mut y, &on_gpu, &x);
  }
  Option<Distinct<Tensor<i32, [?]>>>::None => {
    println!("a token is in the list twice");
  }
}

This is the inspector-executor pattern lifted into the type system: the type persists the verification witness across function boundaries. The program pays for uniqueness checking once at construction, and every subsequent kernel launch takes &Distinct<..> at zero runtime cost. Alternatively, when an algorithm guarantees uniqueness by construction, the producer can wrap the tensor with unsafe { Distinct(tokens) }.

In std::nn, for example, nn_moe_group groups token-expert pairs on the GPU via a counting sort and returns the grouped order wrapped in Distinct. The single unsafe { Distinct(order) } lives inside the library routine, eliminating both the host-side check and any CPU-GPU round-trip in the caller.

How the race checker consumes Distinct. Semantically, Distinct<T> contributes one axiom: idx[a] == idx[b] ⇒ a == b. In src/hir/check/across_proof.rs, every read idx[e] of a Distinct parameter becomes an affine basis variable keyed by the tensor and the affine form of e, so two reads at the same index share one variable. That synthetic variable inherits whichever loop variables e fixes (since two iterations can observe the same element value only if they evaluate the same index e), and then participates normally in the mixed-radix disjointness rules. Consequently, (idx[b] as i64) * 4 + (l as i64) with 0 <= l < 4 fixes b just as b * 4 + l does.

Under the SMT formulation planned in #3561, idx would be modeled as an uninterpreted function idx : Int → Int. Because the race condition only compares two concrete iterations b1 and b2, the query would add the single ground instance idx(b1) == idx(b2) ⇒ b1 == b2 with no quantifiers. The resulting query stays within QF_UFLIA (quantifier-free linear integer arithmetic with uninterpreted functions), a decidable fragment that Z3 supports.

Currently, only the HIR race checker reads the Distinct invariant; both code generators erase Distinct<T> to its underlying tensor, and MLIR optimization passes do not yet exploit it.

Why the escape hatch stays bounded

Many escape hatches have a coarse blast radius. A C loop pragma such as ivdep vouches for every access in the loop, as the section on C shows below. In Vx, an unsafe block does not turn off the race check at all. Distinct isolates an unchecked (or dynamically checked) assumption to a single predicate over a single value, while every surrounding static check remains enforced:

  • Move-only, type-restricted construction. Distinct::check(t) validates uniqueness; Distinct(t) bypasses the check and fails with E5001 outside unsafe. Both accept only 1D integer tensors (E3004) and move t, preventing mutation through any prior alias.
  • Immutable after construction. Writing to an element of a Distinct tensor triggers E4006, preserving injectivity across its entire lifetime.
  • Contracted at the function boundary. Because the invariant sits in the parameter type, callers discharge it and callees rely on it without inspecting each other's bodies—preserving Vx's rule that signatures are self-contained contracts for parallel per-function compilation.
  • Parameter-scoped in the race proof. Today, a read through a Distinct local, a struct field, or a parameter that the body binds again does not fix b.
  • All other accesses remain checked. Each of the following still fails with E6032 even when idx is Distinct:
y[idx[b]][0] = y[b][0] + 1.0;      // another pass may write row b
y[idx[b / 2]][0] = 1.0;                // passes 0 and 1 write row idx[0]
y[idx[b]][0] = y[idx[b + 1]][0];      // pass b + 1 writes that row

A subtle interaction with modular arithmetic. One edge case surprised us: with i64 elements in idx, the write out[idx[b] * 4 + l] is still rejected with E6032. Injectivity over 64-bit integers does not imply injectivity modulo 264 after multiplication by 4, because two distinct i64 indices can collide under wrapping. Widening i32 elements via idx[b] as i64 eliminates wraparound in * 4, so the write compiles. Distinct witnesses element uniqueness, not overflow freedom.

After Distinct::check, safe code cannot break injectivity. With unsafe { Distinct(t) }, a duplicate element violates the soundness precondition and produces a data race with undefined results—that is the exact contract of unsafe. The engineering payoff is audit locality: the trust boundary is a single line at construction time, while the kernel itself contains zero unsafe blocks.

We considered and rejected three alternative designs:

  • A launch-site precondition (requires idx.distinct()). Checking distinctness at every kernel launch forces an O(n) scan per call and does not flow across helper boundaries, whereas Distinct checks once and propagates the witness in the type.
  • Per-write unsafe blocks that turn off the race check. This would suppress the check at each such write, including any real race there, and it documents nothing about idx in the signature.
  • Interprocedural inference from callers. Because idx comes from runtime router outputs, caller bodies do not statically possess the invariant anyway—and peeking into callers violates modular parallel compilation.

What C's restrict and loop pragmas cannot express

Since C99, C's primary mechanism for communicating memory-disjointness facts to the compiler has been restrict. A restrict-qualified pointer promises that, during its lifetime, any object modified through that pointer is accessed exclusively through pointers derived from it. That is a statement about pointers—saying that the memory reached through y, idx, and x does not overlap. Consider the same scatter-add in C with every parameter marked __restrict:

void scatter_add(float *__restrict y, const int *__restrict idx,
                 const float *__restrict x, int n) {
  for (int i = 0; i < n; i++)
    y[idx[i]] += x[i];
}

Compiled with clang 22 at -O3 -march=x86-64-v4, the loop fails to vectorize:

scatter.c:4:15: remark: loop not vectorized: unsafe dependent memory operations in loop

Clang's analysis is sound: restrict speaks only about aliasing between distinct restrict pointers. It has no vocabulary to constrain the data values read through idx, so y[idx[i]] and y[idx[j]]—loaded via the same pointer y—must be treated as potentially aliasing.

To force vectorization or parallelization in C/C++, a programmer must turn off dependence checking for the entire loop via pragmas such as #pragma clang loop vectorize(assume_safety), #pragma GCC ivdep, #pragma omp simd, or #pragma omp parallel for. With assume_safety, Clang emits an 8-wide SIMD gather-add-scatter loop. Running both binaries on 16 elements cycling over 4 rows (each row appearing 4 times, each iteration adding 1.0) shows the cost of a false loop-wide assertion:

plain:          4 4 4 4
assume_safety:  2 2 2 2

This input breaks the pragma's promise, so the compiler owes no particular answer, and nothing warned. The pragmas are compiler and OpenMP extensions outside the C standard. The deeper contrast is granularity: loop pragmas assert non-interference globally across every load and store in the loop body with zero compiler verification. Distinct asserts a single property of a single index tensor, and the compiler verifies every remaining access and arithmetic step against it.

Three structural limitations further restrict C's restrict:

  • Erased from function types. Under C11 §6.7.6.3, top-level qualifiers on parameter types are stripped when checking function-type compatibility, so void f(int *restrict p) and void f(int *p) have identical types and signatures propagate no contract to callers.
  • Absent from standard C++. __restrict remains a non-standard vendor extension.
  • Unchecked UB. Misusing restrict (specified in C11 §6.7.3.1, notoriously subtle and typically lowered only partially via LLVM's noalias parameter attribute) is undefined behavior, with no diagnostic.

What is left

  • Performance tuning of nn_moe_group. The GPU counting sort ran correctly on an H200, and its throughput is still being tuned.
  • Propagating injectivity to MLIR (#3561). The plan marks each store through a Distinct index with an attribute that Vx's MLIR passes read, so loop tiling and fusion can use the same axiom.
  • The MoE combine pass. Combining outputs from multiple experts per token is a scatter-add with intentional collisions, which still requires atomic updates or a dedicated reduction pass.
