The library that only worked on the machine that built it

Aditya Kumar · 22 September 2026

TL;DR: Vx 0.0.1 shipped on 10 September and could only run hello-world on the machine that built it. Both macOS libraries recorded the build runner's directory as their install path, and every program linked against them copied that path. The release smoke test passed because it ran on that same runner, so the broken release stayed up for eleven days. Fixing it uncovered three more bugs, one after another. Here is the whole chain, and two commands that check your own release for the first one.

On 10 September we shipped Vx 0.0.1. Every check was green. For the next eleven days, anyone who ran the install command from our front page on their own machine got this:

$ curl -fsSL https://vxlang.org/install.sh | sh
...
==> Verifying the install
dyld[7851]: Library not loaded: /Users/runner/work/Vx/Vx/target/release/deps/libvx_std_core.dylib
  Reason: tried: (no such file), ...
error: the installed compiler could not run a hello-world program

Look at the path. /Users/runner/work/... is a folder on a GitHub Actions runner: the temporary machine that built the release. That machine was deleted when the release job finished. So the only computer where Vx 0.0.1 worked stopped existing a few minutes after it was built.

This post follows that bug and the three that were hiding behind it. Each fix led straight to the next bug.

Bug 1: the library remembered where it was born

On macOS, a shared library (a .dylib file) stores the path where it expects to be found. The field is called LC_ID_DYLIB. When you link a program against the library, the linker copies that path into the program. When the program starts, the macOS dynamic loader, dyld, reads the path back and goes looking for the library there.

If the build never sets this path, the library gets the full path of the folder it was built in. We never set it for either library. Here is what the 0.0.1 release recorded: 

$ otool -D ~/.vx/toolchains/v0.0.1/lib/libvx_std_core.dylib
/Users/runner/work/Vx/Vx/target/release/deps/libvx_std_core.dylib

$ otool -D ~/.vx/toolchains/v0.0.1/lib/libvx_mlir_shims.dylib
/Users/runner/work/Vx/Vx/target/release/build/vxc-7e805375eee9c913/out/libvx_mlir_shims.dylib

Every toolchain we published carried a piece of the build machine's filesystem inside it. Linux has the same trap under other names: DT_SONAME is the name a library gives itself, and DT_RPATH and DT_RUNPATH tell the loader where to search. Any project that builds shared libraries in CI can ship this bug, on either system.

Why every check was green

Our release workflow already had a smoke test. It unpacked the release archive and ran a program with it. It passed on every release, and it was doing its job correctly.

The problem was where it ran: on the same runner, a few steps after the build. On that machine, /Users/runner/work/Vx/Vx/target/release/deps was a real folder with the real library inside. dyld found exactly what it was told to find, and the program printed the right answer.

The test asked "does this run?" on the one machine in the world where the answer was yes. Running a program only tells you about the machine it ran on. To know whether a release will work somewhere else, you have to read the binaries and see which paths they expect.

The first fix broke a test about parallel loops

The fix has two parts. Each library gets an @rpath install name, which tells dyld to search a list of folders that the program provides. Then the compiler passes an -rpath flag for each folder the program links a library from. Our two libraries live in different folders: the runtime in target/<profile>, and the MLIR shims in the build script's output folder (OUT_DIR).

Our first attempt renamed both libraries but added only one -rpath. That was worse than no fix at all: the shims library now announced a name that nothing could resolve.

The test suite caught it right away, from an unexpected place. host_workers_cover_the_loop_once.vx checks that a parallel loop visits every iteration exactly once. It has nothing to do with packaging. It caught the bug because it builds a real program and runs it, and only a test that runs a built program can see a library that fails to load.

Bug 2: the flag nobody ran

With the first bug in view, we asked what else the smoke test never tried. It compiled hello-world with --run. Nothing ever tried --action emit-obj, which writes an object file.

emit-obj had been broken on Linux for months. The cause was a string handed from Rust to MLIR's C API. A Rust string slice (&str) is a pointer plus a length, with no NUL (\0) byte at the end. The C function mlirExecutionEngineCreate ignored the length, built its StringRef from the pointer alone, and called strlen to find the end. Every runtime library path ran past its real end into whatever heap bytes came next. No library loaded, and no object file was written.

This bug survived testing on macOS, on Linux on EC2, and in an Ubuntu 22.04 Docker container. All three used --run, which takes a different route through MLIR: --run hands the module to mlir-translate and links with Clang, while emit-obj builds an MLIR execution engine inside the compiler. Three environments all tested the same code path, and the bug was on the other one.

Bug 3: the release shipped without core

With both fixes merged, we started the v0.0.2 release. It failed on both macOS and Linux: 

Frontend failed to parse 'uses_std.vx':
  Resolution error: Could not resolve import 'core::ops'

The packaging script copied the standard library from a hand-written list: std and graph. We added core to the repository later, and nobody updated the list. So every release shipped without core. Nobody noticed in development, because a source checkout has the whole tree on disk. The release archive did not, and std::vec imports core::ops.

Bug 4: the fix for bug 3, caught by its own assertion

The fix was to copy every folder under stdlib/ instead of a remembered list. In the same change, we added an assertion that std and core are present before the archive is built.

The assertion failed on its very first run. The glob stdlib/*/ gives each folder name to cp with a trailing slash, and cp -R dir/ dest copies what is inside dir/ and drops the folder itself. Every module landed loose in stdlib/, with no std/ folder left to import from.

Without the assertion, this would have been bug 5, found by users. That is why we now write the assertion in the same change as the code it guards.

What guards the release now

We added four guards. We tested each one by breaking the code it covers and checking that the guard reported it:

  • A unit test that checks our shipped libraries use relocatable @rpath install names.
  • A release step that reads the paths recorded in every shipped Mach-O binary and fails if any of them is a build-machine path. We ran it against the broken v0.0.1 archive, and it caught both libraries.
  • An emit-obj check in the smoke test that looks for the object file on disk. The exit status alone reported success in three different failure modes.
  • A packaging step that copies every folder under stdlib/, with an assertion that std and core made it into the archive.

Check your own release

Nothing here is specific to Vx. If your project builds a shared library in CI and ships it, unpack your release and look at the paths inside: 

# macOS
$ otool -D lib/*.dylib
$ otool -L bin/*

# Linux
$ readelf -d lib/*.so | grep -E 'RPATH|RUNPATH|SONAME'

On macOS, otool -D prints a library's install name and otool -L lists what a program links against. On Linux, readelf -d shows the same information. If any line shows a folder that only exists on your build machine, your release has this bug, and your smoke test is probably green. Ours now prints: 

$ otool -D lib/libvx_std_core.dylib
@rpath/libvx_std_core.dylib

A test that runs a release on the machine that built it is testing that machine. Our release said the toolchain worked, and it was right about the only computer it ever asked.

Vx v0.0.2 is out with all four guards. The install command on the front page now works on macOS (Apple Silicon) and Linux (x86-64): curl -fsSL https://vxlang.org/install.sh | sh. If it fails on your machine, please open an issue on GitHub and include the output.
