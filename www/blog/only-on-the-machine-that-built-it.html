The library that only worked on the machine that built it

Aditya Kumar · 22 September 2026

TL;DR — Vx 0.0.1 shipped on 10 September and could not run hello-world on any machine except the one that built it. Both macOS libraries recorded the release runner's own directory as their identity, and every program linked against them copied that string. The release smoke test passed, because it ran on that machine, and the broken tarball stayed the published one for eleven days. Behind that bug were three more, each hidden by the same habit: testing that something runs, in the place it was made. Here is each one, and the two commands that would have caught the first.

The front page of this site offers one instruction. Someone follows it on a laptop that has never seen the source tree, and this is what they get.

$ curl -fsSL https://vxlang.org/install.sh | sh
...
==> Verifying the install
dyld[7851]: Library not loaded: /Users/runner/work/Vx/Vx/target/release/deps/libvx_std_core.dylib
  Reason: tried: (no such file), ...
error: the installed compiler could not run a hello-world program

That path is not on their machine. It was never on their machine. It is a directory on a GitHub Actions runner that stopped existing the moment the release job finished.

What a dylib remembers

A Mach-O shared library carries the path it expects to be found at, in a load command called LC_ID_DYLIB. When you link a program against that library, the linker copies the string into the program. At startup, dyld reads it back and goes looking.

Neither of our libraries set one. When a library does not say what it is called, it gets called by wherever it happened to be built: 

$ otool -D ~/.vx/toolchains/v0.0.1/lib/libvx_std_core.dylib
/Users/runner/work/Vx/Vx/target/release/deps/libvx_std_core.dylib

$ otool -D ~/.vx/toolchains/v0.0.1/lib/libvx_mlir_shims.dylib
/Users/runner/work/Vx/Vx/target/release/build/vxc-7e805375eee9c913/out/libvx_mlir_shims.dylib

Every toolchain we published carried the build machine's filesystem inside it. ELF has the same mechanism under different names — DT_SONAME for what a library calls itself, DT_RPATH and DT_RUNPATH for where the loader should look — so this is not a macOS problem that Linux is immune to. It is a packaging problem that both formats let you ship.

The smoke test was green, and it was not a bad test

The release workflow already unpacked the tarball and ran a program with it. It passed on every release. It was not a careless test, and it was not broken.

It ran on the machine that built the toolchain, a few steps after building it. There, /Users/runner/work/Vx/Vx/target/release/deps is a real directory with a real library in it, so dyld found what it was asked for and the program printed its answer. The test asserted something true. It just wasn't the thing that needed to be true.

Running an artifact and checking an artifact are different acts. The first asks whether it works here. The second asks what it says about where it expects to live — and only the second survives being copied somewhere else.

The fix broke a test, which is how we found the rest of it

The repair is to give each library an @rpath name, and have the compiler pass an -rpath for the directory it links each one out of. The libraries do not share a directory: in a checkout the runtime sits in target/<profile> and the shims in the build script's OUT_DIR.

The first attempt renamed both and added one rpath. That is worse than not fixing it, because now the shims announced a name nothing could resolve. The suite caught it immediately: host_workers_cover_the_loop_once.vx, a fixture that links a program and checks its answer rather than reading its MLIR, stopped linking.

That fixture exists to prove a parallel loop covers its iteration space exactly once. It has nothing to do with packaging. It caught this because it is one of the tests that runs a built program instead of inspecting compiler output, which turns out to be the only kind that can.

The second question that smoke test never asked

While fixing the first hole we looked at what else the smoke test does not cover. It compiles a hello program with --run, and parses one importing std::vec. Nothing asks for --action emit-obj.

That is not hypothetical. emit-obj was broken on Linux for months. mlirExecutionEngineCreate builds its StringRef from the pointer alone, so it calls strlen and throws away the length it was handed. A Rust &str is not NUL-terminated. Every runtime library path ran off its end into whatever heap bytes came next, no library loaded, and no object file was written.

It survived macOS testing, a native Linux run on EC2, and a Docker 22.04 container. All three exercised --run, which reaches MLIR by a different route: --run hands the module to mlir-translate and links with clang, while emit-obj builds an execution engine in process. Three environments, one code path, and the broken one was the other.

Then the release failed on a third thing

With the fix merged, the v0.0.2 job ran and failed on both platforms: 

Frontend failed to parse 'uses_std.vx':
  Resolution error: Could not resolve import 'core::ops'

The packaging script staged the standard library by a list written by hand: std and graph. core was added to the tree later and nothing updated the list, so every release shipped without it. import std::vec reaches core::ops, which is why this failed in a released toolchain while passing in every checkout, where the whole tree is simply there.

And that fix shipped a bug its own assertion caught

The repair is to stage every directory under stdlib/ rather than a remembered list, and to assert that std and core arrived before building the tarball.

The assertion failed on its first run. Globbing stdlib/*/ hands cp a trailing slash, and cp -R dir/ dest copies the contents of the directory rather than the directory. Every module spilled flat into stdlib/, leaving no std/ for a program to import.

Five minutes older than the bug it caught. This is the argument for writing the assertion at the same time as the thing it guards, rather than after you believe the thing works.

What is in place now

Four guards, each one verified by breaking the code it covers and watching the right assertion report:

  • A unit test that our shipped libraries name themselves relocatably.
  • A release step that reads what every shipped Mach-O records and fails the release if any of it names a build-machine path. Validated against the broken v0.0.1 tarball, where it fails and names both libraries.
  • An emit-obj assertion in the smoke test that checks for the object file rather than the exit status — that arm reported success in three distinct failure modes before it was written this way.
  • Standard library staged by iterating the directory, with an assertion that std and core are present.

Two commands, on your release rather than ours

Nothing above is specific to Vx. Any project that builds a shared library in CI and ships it can publish the build machine's filesystem by accident. Unpack your own release and ask what it recorded: 

# macOS
$ otool -D lib/*.dylib
$ otool -L bin/*

# Linux
$ readelf -d lib/*.so | grep -E 'RPATH|RUNPATH|SONAME'

If any of it prints a directory that exists only on the machine that built it, your release has this bug, and your smoke test is probably green. Ours says this now: 

$ otool -D lib/libvx_std_core.dylib
@rpath/libvx_std_core.dylib

A test that runs an artifact on the machine that produced it is testing the machine. Our release said the toolchain worked, and it was right about the only computer it ever asked.

v0.0.2 is out, with all four guards in it. The install line on the front page now leads somewhere: curl -fsSL https://vxlang.org/install.sh | sh, on macOS with Apple Silicon or Linux x86-64. If it fails on your machine, that is a bug worth filing — with the output, which is more than we gave anyone for eleven days.
