Asking the other compiler

Aditya Kumar · 22 September 2026

TL;DR — Two impls of one trait for one type collided on a single mangled name in Vx, and the call was refused because nothing could say which was meant. Choosing between them looked like a language design decision, so I compiled the same program in Rust to see what Rust had decided. Rust decides nothing: it infers the argument's type first, and then exactly one impl applies. The untyped literal case it settles with a blunt fallback to i32. Vx already did that part, so the decision had already been made without anyone noticing.

The most useful hour of this change was spent not writing Vx. It was spent writing forty lines of Rust and reading what came out of rustc.

Two impls, one name

A method's mangled name in Vx was the receiver and the method: i64$from. Nothing of the trait was in it, so a trait stamped once per argument type collided with itself:

impl From<i32> for i64 { .. }   // i64$from
impl From<u8>  for i64 { .. }   // i64$from, again

The second was dropped by a by-name deduplication before its body was ever emitted, and the call site refused the pair outright, which was the right thing to do with a name that meant two functions. It also made the shape unwritable, and core::convert is built out of exactly that shape — From stamped from a table of widenings. The module was waiting on it.

The part that looked like a decision

Putting the trait in the name is mechanical. What follows it is not. Given

i64::from(7)

and candidates taking i32 and u8, which one does the call mean? The literal fits both. I wrote this up as needing "selection among same-named candidates by parameter type", which sounds like C++ overload resolution — a ranking of conversions, a notion of a best match, tie-breaking rules. That is a large thing to add to a language, and it is the kind of decision you want to get right once.

Then it occurred to me that another compiler had already made it.

Compiling the question

The orphan rule stops you writing that exact pair in Rust, so the shape goes through a local trait. Three calls, and each impl returns a number naming itself:

trait MyFrom<T> { fn my_from(v: T) -> Self; }

impl MyFrom<i32> for i64 { fn my_from(_v: i32) -> i64 { 32 } }
impl MyFrom<u8>  for i64 { fn my_from(_v: u8)  -> i64 { 8 } }

fn main() {
    println!("literal      -> {}", i64::my_from(7));
    println!("typed u8     -> {}", i64::my_from(7u8));
    let n: u8 = 7;
    println!("u8 variable  -> {}", i64::my_from(n));
}

It compiles, which was the first surprise — I had half expected an ambiguity error:

literal      -> 32
typed u8     -> 8
u8 variable  -> 8

So the untyped literal reaches the i32 impl and a typed argument reaches its own. Two more things are worth reading directly. The first is the object file:

__RNvXCs..._1b  x  INtB2_6MyFrom l E  7my_from     <i64 as MyFrom<i32>>::my_from
__RNvXs_Cs..._1b x INtB4_6MyFrom h E  7my_from     <i64 as MyFrom<u8>>::my_from

v0 mangling encodes the self type, the trait, and the trait's arguments. x is i64; l and h are i32 and u8. I confirmed that position by swapping u8 for u16 and watching h become t. So the first half of the Vx fix — put the trait in the name — is simply what Rust does, and needed no decision at all.

The second is what happens when the fallback has nowhere to land. Same two impls, written for u8 and u16, with no i32 impl:

error[E0277]: the trait bound `i64: MyFrom<i32>` is not satisfied
help: the following other types implement trait `MyFrom<T>`
      `i64` implements `MyFrom<u8>`
      `i64` implements `MyFrom<u16>`

Not an ambiguity error. Rust falls back to i32 regardless, fails the concrete bound, and lists the impls that do exist.

What Rust actually does, which is less

There is no overload resolution here. i64::my_from(7) produces an obligation i64: MyFrom<?T> with an inference variable, and the argument's type fixes ?T. By the time an impl is looked up there is exactly one candidate, so there is nothing to choose between and no ranking to define.

The literal is handled by integer fallback: an integral inference variable still unresolved at the end of type checking defaults to i32, and only then is the obligation re-checked. It is a blunt rule with a plain failure mode, and it is the whole of the design decision I thought I was facing.

The part that made this cheap rather than merely informative: Vx already defaults an uncontexted integer literal to i32. let x = 7; has always been an i32. So the rule was already in the language, put there for unrelated reasons, and the work reduced to narrowing candidates by a type that was already decided.

The same program, in Vx

This is the test fixture from the change, word for word, so it will run on every commit once that lands. Each body returns a digit naming itself, and print writes no separator, so the three calls read as one line:

trait Build<T> {
  fn make(v : T) -> Self;
}

impl Build<i32> for i64 {
  fn make(v : i32) -> i64 {
    return 1;
  }
}

impl Build<u8> for i64 {
  fn make(v : u8) -> i64 {
    return 2;
  }
}

impl Build<u16> for i64 {
  fn make(v : u16) -> i64 {
    return 3;
  }
}

fn main() -> i32 {
  // No annotation: the literal is i32, so the i32 impl runs.
  print(i64::make(7));
  let b : u8 = 3;
  print(i64::make(b));
  let s : u16 = 9;
  print(i64::make(s));
  return 0;
}

It prints 123. And the case where the fallback lands on nothing reports what exists rather than an ambiguity, which is the same answer Rust gives in a different accent:

Error[E3036]: No impl of 'make' on 'i64' takes (i32); 'i64' implements Build<u16>, Build<u8>

The rule I got wrong first

My first cut put the trait segment on every trait-impl method. That renamed the standard library's entire scalar math, because abs on an f32 comes from impl Math for f32 — a trait impl like any other. About forty fixtures went red, none of them for a reason I had anticipated.

The fix is not to update forty fixtures. Two impls of one trait for one type can differ in nothing but the trait's arguments, so a trait without arguments can be implemented for a type at most once and cannot collide with itself. The segment is only needed when the trait has arguments. impl Math for f32 keeps f32$abs; impl Build<i32> for i64 becomes i64$Build$i32$make. That is the whole rule rather than a convenience, and it leaves the other collision class exactly where it was: two different traits supplying one method name still share a name, and are still refused at the call site.

What the greps missed

Six fixtures pinned the old spelling of a method on an argument-bearing trait. I found all six by running the test suite. I found none of them by searching, and I searched three times.

  • Sweeping for affected fixtures, I grepped one enum variant name — GpuHbm — and missed NPUHBM, which a fixture was pinning. The suite found it.
  • Checking a change's blast radius across 66 files, I ran vxc with an invalid --action. Every run died on the argument, printed no diagnostics, and reported a reassuring zero.
  • Verifying fixtures by hand, I ran the default backend. The harness appends --legacy-codegen to backend fixtures, so I was checking a different code generator than the one the assertions were written against — which sent me looking for a regression in my own change that did not exist.

There is a fourth, of a piece with these: twice I piped cargo test into grep and read the exit code, which belongs to grep. A suite with a failing test reported success, and I passed that on before catching it. The exit code now gets written into the log where nothing can launder it.

None of these were subtle once seen. All of them produced a green result that meant nothing, which is the failure mode worth designing against — a check that cannot fail is indistinguishable from one that passed.

The part worth keeping

The thing I would do again is the hour of Rust. A language decision is expensive to make and more expensive to revisit, and there was a compiler on this machine that had already made it, shipped it, and had it used for a decade. Reading its answer cost forty lines and one nm invocation, and it replaced a design argument with a measurement.

It also made the answer smaller than the question. I had written down "selection among same-named candidates by parameter type" and imagined a ranking. What was needed was: infer the argument, then look up one impl, and default a bare integer literal to i32 — a default the language already had.

The change is Vx#709, the issue is Vx#686, and the Rust findings are written up in a comment on it. Instance dispatch still does not narrow by argument type, which is the obvious follow-up and is recorded in the fixtures rather than left to be discovered.
