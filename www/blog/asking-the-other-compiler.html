Asking the other compiler

Aditya Kumar · 22 September 2026

TL;DR — In Vx, two implementations of the same trait collided on a single mangled symbol name when they differed only by parameter type. Resolving calls between them initially seemed to require C++-style overload resolution. Testing the same pattern in Rust revealed a simpler answer: type inference resolves the argument type first, leaving exactly one matching implementation. Untyped integer literals resolve through integer fallback to i32. Fixing the bug took two things: encoding trait arguments into mangled names, so the implementations become distinct functions, and narrowing candidates by argument type at the call site. Vx already defaulted untyped integer literals to i32, so that rule cost nothing.

The most productive hour of this fix was writing forty lines of Rust and inspecting what rustc emitted.

Two implementations, one mangled name

Vx generated method symbols by combining the receiver type and the method name: <receiver>$<method>. Because the mangled name omitted the trait, multiple implementations of the same trait with different argument types produced identical symbols:

impl From<i32> for i64 { .. }   // i64$from
impl From<u8>  for i64 { .. }   // i64$from, again

A deduplication pass dropped the second implementation before emitting its body. Call sites then rejected the call because two functions shared one name. This collision blocked work on core::convert, which defines widening conversions for primitive integers by stamping out From across integer types.

Why this looked like a language design problem

Encoding trait information into symbol names is straightforward engineering. Call-site resolution seemed harder. Consider this invocation:

i64::from(7)

When candidates exist for both i32 and u8, which implementation should the compiler select? The literal 7 fits into both types. Resolving this appeared to require selection among same-named candidates by parameter type — full C++-style overload resolution with conversion ranks, best-match scoring, and tie-breaking rules. Adding overload resolution changes the core semantics of a language, and getting it right is difficult.

Before designing a complex resolution system for Vx, I checked how Rust handles this exact pattern.

Testing the pattern in Rust

Rust's orphan rule prevents implementing an external trait like From for primitive types in user code, so the test uses a local trait named MyFrom. Each implementation returns a distinct integer:

trait MyFrom<T> { fn my_from(v: T) -> Self; }

impl MyFrom<i32> for i64 { fn my_from(_v: i32) -> i64 { 32 } }
impl MyFrom<u8>  for i64 { fn my_from(_v: u8)  -> i64 { 8 } }

fn main() {
    println!("literal      -> {}", i64::my_from(7));
    println!("typed u8     -> {}", i64::my_from(7u8));
    let n: u8 = 7;
    println!("u8 variable  -> {}", i64::my_from(n));
}

The program compiles without error and runs:

literal      -> 32
typed u8     -> 8
u8 variable  -> 8

The untyped literal selects the i32 implementation, while explicit types select the matching type. Inspecting the compiled object file with nm shows how Rust names the symbols:

__RNvXCs..._1b  x  INtB2_6MyFrom l E  7my_from     <i64 as MyFrom<i32>>::my_from
__RNvXs_Cs..._1b x INtB4_6MyFrom h E  7my_from     <i64 as MyFrom<u8>>::my_from

Rust's v0 mangling format encodes the self type, the trait name, and the trait arguments. In these symbols, x represents i64, while l and h represent i32 and u8. Changing u8 to u16 changes h to t. Rust avoids symbol collisions by including the trait arguments in the mangled name.

The second question is what happens when no implementation matches the default integer type. Compiling the same program with implementations for u8 and u16, omitting i32, produces this diagnostic:

error[E0277]: the trait bound `i64: MyFrom<i32>` is not satisfied
help: the following other types implement trait `MyFrom<T>`
      `i64` implements `MyFrom<u8>`
      `i64` implements `MyFrom<u16>`

Rust reports an unsatisfied trait bound. The compiler assigns i32 to the literal, evaluates the concrete bound i64: MyFrom<i32>, fails, and lists the available implementations.

How type inference avoids overload resolution

Rust resolves this call site without overload resolution. When the compiler evaluates i64::my_from(7), it creates a trait obligation i64: MyFrom<?T> containing an unbound inference variable ?T. Resolving the argument type determines ?T. Once ?T has a concrete type, trait lookup finds exactly one matching implementation, removing the need to rank candidate methods.

Untyped literals rely on integer fallback. If an integer inference variable remains unresolved at the end of type checking, the compiler defaults it to i32 and re-evaluates the obligation. This single fallback rule replaces an entire overload resolution subsystem.

This behavior simplified the fix for Vx: Vx already defaults uncontexted integer literals to i32. Statements like let x = 7; have always produced an i32. Because the fallback rule already existed in the language, method resolution only needed to infer argument types before looking up implementations.

The working program in Vx

The pull request includes this test fixture directly from the change. Each implementation returns a number identifying itself, and print writes numbers without separators:

trait Build<T> {
  fn make(v : T) -> Self;
}

impl Build<i32> for i64 {
  fn make(v : i32) -> i64 {
    return 1;
  }
}

impl Build<u8> for i64 {
  fn make(v : u8) -> i64 {
    return 2;
  }
}

impl Build<u16> for i64 {
  fn make(v : u16) -> i64 {
    return 3;
  }
}

fn main() -> i32 {
  // No annotation: the literal is i32, so the i32 impl runs.
  print(i64::make(7));
  let b : u8 = 3;
  print(i64::make(b));
  let s : u16 = 9;
  print(i64::make(s));
  return 0;
}

Running the program outputs 123. When fallback targets an unimplemented type, Vx mirrors Rust by listing existing implementations:

Error[E3036]: No impl of 'make' on 'i64' takes (i32); 'i64' implements Build<u16>, Build<u8>

What went wrong: breaking scalar math

My initial implementation mangled trait names onto every trait method unconditionally. That change broke the standard library's scalar math. In Vx, abs on an f32 comes from impl Math for f32, which is a standard trait implementation. Mangling the trait name renamed every math method in the standard library, breaking roughly forty test fixtures.

Updating forty fixtures would have codified the wrong rule. Two implementations of the same trait for one type can differ only in their trait arguments. A trait without type arguments can only be implemented once for any given type, so its methods can never collide with themselves. The mangling rule only needs to append trait information when the trait takes arguments.

Under the revised rule, impl Math for f32 retains the symbol f32$abs, while impl Build<i32> for i64 becomes i64$Build$i32$make. Methods from two distinct traits that share a name still produce a collision and are rejected at the call site.

What the test suite caught and grep missed

Six fixtures pinned the old symbol names for methods on argument-bearing traits. Running the test suite caught all six fixtures. Three separate manual searches across the repository missed every one.

During the fix, four separate checks produced false confidence by reporting success when they should have failed:

  • Incomplete search terms: While checking for affected fixtures, I grepped for the enum variant GpuHbm and missed NPUHBM, which a fixture was pinning. The test suite caught the mismatch.
  • Searching output that was never produced: To assess the blast radius across 66 files, I ran vxc with an invalid --action flag. Every run rejected the flag and exited 2, printing an argument error instead of compiling anything. My sweep grepped that output for a diagnostic code, found none, and reported zero affected files. It never looked at an exit code.
  • Testing against the wrong backend: While checking fixtures by hand, I ran the default code generator. The test harness appends --legacy-codegen to backend fixtures, so manual runs tested a different backend than the automated assertions, triggering a hunt for a phantom regression.
  • Laundering exit codes through pipes: Twice I piped cargo test into grep and checked the command's exit code, which reflected grep rather than the test runner. A suite with a failing test reported success. The test script now writes runner exit codes directly to the log.

Each check returned a successful result without performing a valid test. A check that cannot fail provides no useful signal, making silent pass states the most critical failure mode to eliminate.

Measuring existing compilers

Studying Rust saved significant language design effort. Deciding how a language resolves calls is costly to implement and difficult to change later. Rust solved this problem a decade ago. Writing forty lines of code and running nm replaced open-ended language debate with an empirical measurement.

The investigation also produced a much simpler implementation. A full overload resolution system with candidate ranking was unnecessary. The actual requirement was straightforward: resolve argument types through inference, select the single matching implementation, and apply the existing i32 fallback for bare integer literals.

The change is Vx#709, the issue is Vx#686, and the Rust findings are documented in a comment on the issue.
