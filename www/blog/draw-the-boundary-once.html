Draw the boundary once

Aditya Kumar · 27 October 2026

TL;DR — Visibility rules, the build system and the package manager all read one thing: the public interface of a package. When a language designs them apart, they disagree about where that interface is, and the disagreement lasts for the life of the language. This post shows that drift in C++, Java, Rust, Swift and Go, and writes the contract between a compiler and a build system as one equation. It scores 15 compiler and build-system pairs against the six tests that follow from the equation. None passes all six, and Vx does not either, yet.

A language has three tools that decide what crosses a boundary in a program. Visibility rules (pub, private, crate-visible) decide which code may call a function. The build system decides what to rebuild when a file changes. The package manager decides which versions of a dependency fit together.

All three read the same thing: the public interface of a package. When a language designs them apart, they disagree about where that interface is. The disagreement then lasts as long as the language does. I am designing Vx, so I want to draw that boundary once.

Three tools, one interface

Each tool asks one question. Each answer depends on the public interface of a package.

ToolThe question it asksWhat it needs to know
Visibility rules (the compiler)May this code call that function?Which items are public, and to whom
Build systemThis file changed. What must I rebuild?Whether the change touched an interface that other code uses
Package managerCan version 1.4 replace version 1.3?Whether the public interface changed in a way that breaks callers

If the language states the interface exactly, the build system and the package manager can compute their answers from it. If the language does not, each tool guesses. The guesses disagree, and the programmer settles each disagreement by hand.

Where the boundaries drift

Every popular language shows at least one place where these tools disagree. Each example below is still visible in that language today.

C++: private does not mean hidden

A private field sits in the header, next to the public ones. Change it, and every file that includes the header recompiles. Every binary built against the old layout may break too. The language calls the field private, but the build system and the binary interface treat it as public. Programmers hide it by hand with the pimpl idiom. They move the private fields into a separate struct, and the header keeps only a pointer to it.

C++ also has three visibility systems that do not know about each other. Access specifiers (public, private) control names. Linkage (static, unnamed namespaces) controls object files. Symbol visibility (-fvisibility=hidden, __declspec(dllexport)) controls shared libraries. The language has no package at all.

C++20 modules tried to add a boundary. Every build system then had to learn a new step: scan each file for its imports before compiling anything. CMake shipped stable support in version 3.28, in December 2023, three years after the standard.

Java: the jar had no boundary

Java had package-private visibility from the start. The unit that people shipped, the jar, had no boundary at all. Every public class in every jar on the classpath was visible to every other jar. Libraries came to depend on JDK internals such as sun.misc.Unsafe.

Java 9 added modules, with an exports list, in 2017. That was 21 years after Java 1.0. By then so many libraries used sun.misc.Unsafe that Java 9 kept it reachable. A Maven dependency and a Java module still have two different names.

Rust: build speed decides the public API

Rust comes close. A crate is the unit of compilation, pub(crate) is a visibility level, and a Cargo package usually holds one library crate. The friction starts when a crate grows. A large crate compiles slowly, so teams split it into several crates. Rust has no visibility level for “the crates in my workspace”. So every pub(crate) item that crosses the new line must become pub. If the library is published, crates.io needs each new crate published too. A decision about build speed widens the public API, and the package manager must version it.

Macros cross the same line. A derive macro generates code inside the user's crate, so every helper that the code calls must be pub. serde keeps those helpers in a module hidden from its docs: #[doc(hidden)] pub mod __private. Since version 1.0.225, the module name also carries serde's patch number, as in __private228.

Cargo does not check semver either. A request for that check has been open in Cargo since 2014. Today a separate tool, cargo-semver-checks, does the work.

Swift: a visibility level added to match the package

Swift's internal means “this module”. A Swift package holds many modules. Code shared between two modules of one package had to be public, which made it visible to every user of the package. Swift 5.9 added a package access level in 2023 (SE-0386), nine years after Swift 1.0. The language changed its visibility rules to match its package manager.

Go: one boundary, with versions added later

Go comes closest to one boundary. A package is a directory, the unit of compilation and the unit of visibility. A name that starts with a capital letter is exported. The go command enforces internal/ directories, so the build tool itself checks a visibility rule. An import path is also the place to fetch the code from.

Versions came last. Go ran for six years without them, until modules arrived as an experiment in Go 1.11 in 2018. Go then put the major version into the import path: from version 2 on, a module path ends in /v2, /v3 and so on. To the compiler, a new major version is a new package. That keeps the three tools in agreement. The price is a change to every import at each major release.

The pattern

Every example has the same shape. One tool draws a boundary that the other two cannot see. The programmer then pays in one of three ways:

  • Visibility widens to suit the build. Rust teams make items pub to split a slow crate. Swift code became public to cross a module line.
  • The build does extra work because visibility says too little. A C++ header change rebuilds files that never use the changed field.
  • The package manager trusts a promise that nobody checks. A version number says “compatible”, and a person decided that by reading a diff.

These costs last because code grows around a boundary. Once a thousand libraries call sun.misc.Unsafe, the language cannot hide it. Java needed 21 years to add modules, and Swift needed nine years to add package. C++ is still moving to modules. A language draws its boundaries once, before its users arrive. After that, it can only add exceptions.

The rule that serves all three

The build system and the package manager can compute an answer from the interface only if the interface is written down. Vx already has the rule that makes this true: a signature is the whole contract. Every parameter type and return type is written out. Nothing in a function's interface comes from its body.

Vx made this rule for its parallel compiler. The compiler collects every signature, type and trait implementation first. Then it checks all function bodies in parallel against that fixed table. The same rule gives the other two tools what they need:

  • Build system. The public interface is the set of public signatures, type layouts and trait implementations. None of it comes from a function body. When a change leaves that set the same, the build system can skip checking the code that depends on it. Only generic and inlined bodies need new machine code.
  • Package manager. A tool can compare two versions by their signatures and type layouts, without reading any function body.

Rust shows what happens without the rule. An async fn hides its real return type, and whether that type is Send comes from the body. Change one line in the body, and the returned future can stop being Send. Every caller that sends it to another thread then fails to compile, though the signature did not change. Rust's own design for impl Trait calls this “a silent breaking change” (RFC 1522). A tool that compares signatures cannot see it. C++ has the same problem with auto return types, and with templates, whose bodies sit in headers.

How Vx draws the boundary once

Today Vx has pub items and private items. The rest of this section is the design, and most of it is not built yet.

One manifest, one set of levels

The manifests define two units. A package is a set of modules that the compiler checks as one and the registry publishes as one. A workspace is a set of packages that the registry publishes together, at one version. Each member's manifest names its workspace, and the workspace's manifest sets the version. The visibility levels name the same units:

fn helper()        // private: this module only (the default)
pkg fn plan()      // any module in this package
ws fn lower()      // any package in this workspace
pub fn compile()   // exported: anyone who depends on the package

A workspace is a fact about visibility and release, and no build system can change it. Build one package alone, the whole workspace, or a monorepo of many workspaces: the errors and the program stay the same. Membership does not depend on where files sit on disk either. Cargo finds a member's workspace by searching parent directories. Vx reads the name from the member's manifest.

Kotlin fails this test. Its internal level means “the same module”, and a module is whatever set of files the build tool compiles together.

The word also means more than it does in Rust. A Cargo workspace is a build unit: its members share a lockfile and an output directory. A shared version is optional, and each member can have its own. A Vx workspace requires the shared version, because ws depends on it. Suppose package A 1.2 calls a ws function in package B, and B 1.3 changes that function. With separate versions, a user could get A 1.2 with B 1.3. The build would break, and nothing in the version numbers would warn about it. With one version, that pair cannot exist. The compiler checks it as well: a ws access needs the same workspace name and version in both packages.

So a team can split a slow package inside its workspace and use ws where Rust forces pub.

pub means exported, and the compiler checks it

Every pub item must be reachable from outside the package, or the compiler reports an error. In Rust, a pub item inside a private module is unreachable, and only an optional lint (unreachable_pub) reports it. A signature can name only types that are at least as visible as the signature itself.

Code that a macro generates gets the visibility of the place where the macro is defined. So a macro never forces a helper to be pub, as serde's derive macro does. The public API is then exactly the set of pub items, and a tool can print it.

The version number is computed

A tool compares the public interfaces of two releases. It reports the smallest version bump that is safe. The bump depends on two things: the kind of change, and the visibility of the changed item.

  • A change to a private or pkg item needs at most a patch release.
  • A ws item crosses packages, but its workspace releases at one version. So it carries no semver promise.
  • Only a breaking change to a pub item forces a major release.

Elm already works this way for source code. elm publish refuses a version number that does not match the API diff (Elm compiler source). A first version of the Vx tool is in review as #2258: vx-api diff old.vxlib new.vxlib. Until pkg and ws exist, it treats every item in the interface as public.

Binary compatibility needs a second check, because the layout of a type matters too. A new private field in a public struct breaks no source code, but it changes the struct's size. That is the C++ header problem again. So the tool will check source compatibility and binary compatibility separately.

Where the build system fits

The compiler is a function, and the build system calls it. The language defines what goes in and what comes out. For a package p, the whole contract is one equation:

(Op, Ip) = vxc(Sp, Mp, c, { view(Id, p) | d ∈ deps(p) })

On the right are the inputs. Sp is the source files of p, Mp is its manifest, and c is the build settings, such as the target. deps(p) is the set of packages that Mp lists, and the standard library is one of them.

On the left are the outputs. Op is the machine code. Ip is the interface: every signature, type layout and trait implementation in p, each with its visibility level. Ip also carries the bodies of generic and inline functions, because the packages that use them generate machine code from them.

A dependency d shows p only part of its interface:

view(Id, p) = { x ∈ Id | vis(x) = pub }
             ∪ { x ∈ Id | vis(x) = ws ∧ W(d) = W(p) }

Here W(p) is the workspace of p: its name and its version. So p sees every pub item of d. It also sees the ws items when both packages are in the same workspace at the same version.

The build system evaluates the first equation for every package, in any order that puts a package after its dependencies. Because vxc is a function in the mathematical sense, the order, the parallelism and the cache cannot change the result. Four rules keep vxc a function:

  1. The compiler reads only declared inputs. vxc reads a package's sources, its manifest, and the interface files of its dependencies. It reads nothing else: no search in the current directory, no build scripts, and no comptime code that reads files.
  2. The interface file is the handoff. A dependent compile reads only the interface file of each dependency. The file records the package, its workspace name and version, and every item with its visibility level. A signature is the whole contract, so vxc can write this file before it checks any function body. Dependents can then start early.
  3. The package is the build system's unit. The build system schedules packages, never files. Inside a package, vxc checks function bodies in parallel. Much of rustc's front end runs on one thread per crate, which is one big reason Rust teams split crates. A Vx package can use all cores, so its size alone gives no reason to split it.
  4. The package graph comes from manifests alone. An import textkit::runs must name a package that the manifest lists, or vxc reports an error. The build system never scans source files to find dependencies, as C++20 modules require.

Parts of this exist today. vxc takes each dependency as --package textkit=../textkit, and vxc --emit-interface writes an interface file (.vxlib).

The rebuild rule follows from the equation. The build system compiles p again exactly when one of its inputs changed:

rebuild(p)  ⇔  ΔSp ∨ ΔMp ∨ Δc ∨ ∃ d ∈ deps(p) : Δview(Id, p)

A private or pkg item appears in no view, so a change to it rebuilds nothing outside its package. A ws item appears only in the views of workspace members.

The package manager uses the same views. It compares what a package outside the workspace sees, the pub items alone, in the old version and the new one:

bump(p) = max { b(δ) | δ ∈ diff(viewout(Ipold), viewout(Ipnew)) }

Here b(δ) is the bump that one change δ needs: patch, minor or major. With no change in the pub items, the bump is a patch. Rebuild scope and version bump then follow the same order:

Changed itemWhat rebuildsVersion bump
private or pkgNothing outside the packagePatch at most
wsMembers of the workspaceNo semver rule: one shared version
pubEvery package that depends on itMajor only if the change breaks callers

So vx build is one implementation of a written contract. Bazel or Buck2 can call vxc directly and get the same result.

C libraries are the open case. Rust finds them with a build script, build.rs, which runs arbitrary code during the build. Vx can keep rule 1 with a manifest entry that names the library and its headers.

Visibility sets the exported symbols

The four visibility levels also decide which symbols a shared library exports.

LevelSymbol in a shared library
privateInternal, never exported
pkgHidden
wsExported, with a private version tag, like glibc's GLIBC_PRIVATE
pubExported, with a public version tag

A build setting can make a symbol less visible than its level, but never more visible. An executable hides everything except its entry points. The linker's idea of visibility comes from the language. Vx needs no separate symbol visibility system like the one in C++.

How today's tools score

The equations give six tests. I checked 15 well-known pairs of compiler and build system against them, and none passed all six.

  1. Function: the compile and the build read only declared inputs.
  2. Interface: a dependent compile reads only an interface file, and nothing in that file is inferred from a function body.
  3. Cutoff: a change to a private item or a function body rebuilds no other package.
  4. Graph: the build system learns the package graph without scanning source files.
  5. Visibility: what is visible does not depend on what the build tool compiles together.
  6. Bump: the package manager computes the version bump from the interface diff.

✓ passes, ◐ passes in part, ✗ fails, – does not apply. Scores are as of 25 October 2026, and some partial scores are judgment calls. The scorecard page gives the reason and a source for every cell.

No pair passes the first test. Every one has a hidden input somewhere. Bazel's sandbox still lets an action read the host file system, and it allows the network by default. Elm solves a package's version ranges against the live registry.

Every other test has a winner, but no pair holds all the wins. The two leaders get there in opposite ways. Elm has one author for its compiler, its build tool and its package manager, and both of its checks are short. Bazel gets a cutoff for Java by rebuilding an interface from the bytecode, because Java never defined one.

Some cutoffs are lost between the compiler and the build tool. Clang can write a byte-identical module interface file. But compilers rewrite the file on every compile, and Ninja decides by timestamp, so every edit to a C++ interface unit recompiles every importer. Rust's metadata file records private items and a hash of each source file. An edit to a private function body changes it, so the cutoff in Bazel and Buck2 cannot fire.

Vx scores 0 today too. The compiler reads 19 environment variables, and 15 of them can change the program it builds or the tool that builds it. It also finds tools through PATH, and it searches the current directory for the standard library. The design must pass the two tests that the leaders fail: Function and Bump. Two changes in review start on them. #2255 stops reading the standard library and imports from the current directory, and #2258 adds vx-api diff. #2250 tracks the rest of the hidden inputs.

The three tools can stay separate programs with separate jobs. They agree because they read one definition of the interface, which the programmer writes once.
