How Vx uses MLIR

Five stages from surface syntax to LLVM IR and PTX
Stage 1 · Frontend
Vx Source & Macro Expansion
Parses syntax, expands macro_rules, and checks tensor shapes, placements, and ensures contracts.
↓
Stage 2 · Flat HIR
Typed High-Level IR & .vxlib Archives
Borrow checking, compile-time evaluation (comptime), and race checking. Libraries ship as verified .vxlib files.
↓
Stage 3 · Vx Dialect
TableGen-Defined vx.* Operations
vx.spawn, vx.transfer, and vx.alloc encode execution topology and memory hierarchy.
↓
Stage 4 · Upstream MLIR
linalg · affine · scf · vector · math · gpu · nvvm · llvm
Where mlir! blocks live. Inlined by vx-inline and fused alongside compiler-generated IR.
↓
Stage 5 · Codegen
CPU Machine Code & GPU PTX
LLVM backend for host CPUs (x86_64, AArch64); MLIR NVVM pipeline for GPU kernels.
Why Stage 4 is the Sweet Spot
Library code enters the pipeline before loop fusion, vectorization, and target lowering.

In C or Rust, inline assembly enters at the very bottom of the compiler, after the middle-end optimizer is done. By embedding upstream MLIR dialects directly in library functions, standard library operations participate in high-level passes.

The Problem
Vx Compiler · MLIR Backend

Three ways a library reaches the hardware

Why standard libraries get stuck between compiler intrinsics, per-ISA assembly, and libc
Way 1 · Inline Assembly
Opaque per-ISA strings
asm("popcnt %1, %0"
    : "=r"(r)
    : "r"(x));
Direct hardware access, but the middle-end optimizer cannot see inside it. Every target ISA (x86_64, AArch64, PTX) needs its own assembly string and register constraints.
Opaque to loop & vector passes
Way 2 · Compiler Builtins
Hardcoded in the frontend
__builtin_popcount(x)
__atomic_fetch_add(
    p, 1, __ATOMIC_SEQ_CST)
The optimizer understands them, but every new intrinsic requires plumbing across the lexer, parser, type checker, HIR, and code generator. A library author cannot add one.
Bottlenecked on compiler engineers
Way 3 · Platform Libraries
External C / ABI calls
extern "C" {
  fn sqrtf(x: f32) -> f32;
  fn expf(x: f32) -> f32;
}
Delegates to libm or libc written in C and assembly. Breaks freestanding targets: inside a GPU kernel with no libc, there is nothing to link against.
Fails on freestanding GPU kernels
Way 4 · Vx The mlir! block: library-authored inline IR that is verified, inlined, and lowered across targets.

The Core Thesis
Part I · Design & Compilation Model

An mlir! block is inline assembly whose instructions are MLIR operations.

The library author writes it. vxc checks its contracts, parses and verifies the MLIR, inlines the body, and optimizes it together with the user code around it.

01 · Named SSA
Bind Vx expressions directly to typed MLIR SSA values.
02 · Checked Effects
clobbers and ensures prove safety in parallel loops.
03 · Zero-Special-Case IR
Emitted as a private func.func so standard MLIR passes work untouched.
04 · Multi-Target
One block lowers to CPU instructions, GPU SMEM, or GPU HBM.

Anatomy of an mlir! block

Six explicit boundary clauses between Vx's type system and MLIR's SSA body
stdlib/core/num.vx · stdlib/std/tensor.vx Pure vs. Mutating Block 
// 1. Pure value-returning block (core::num)
fn count_ones(self : i32) -> i32
  ensures(result >= 0 && result <= 32)
{
  return mlir!(
    inputs   : (%a = self : i32),
    returns  : i32,
    ensures  : [writes_only()],
    dialects : ["math"]
  ) {
    %r = math.ctpop %a : i32
    macro.yield %r : i32
  };
}

// 2. In-place tensor mutation (std::tensor)
fn fill(self : &mut Tensor<$t, [?], Memory::M>, v : $t) {
  mlir!(
    inputs   : (%val = v : $t, %out = self : memref<?x$t>),
    clobbers : [self],
    dialects : ["linalg"]
  ) {
    linalg.fill ins(%val : $t) outs(%out : memref<?x$t>)
  };
}
inputs
Binds Vx expressions (self, v) to named SSA values (%a, %out) with explicit MLIR types.
returns
Gives the Vx type of the block’s result. Blocks that only mutate memory omit returns.
clobbers
Lists Vx variables mutated by the block (such as self) so the borrow checker and comptime interpreter track writes.
ensures
Declares memory & concurrency contracts (writes_only(), atomic(t)) verified against the MLIR body.
dialects
Declares the MLIR dialects ("math", "linalg", "nvvm") required to parse and verify the block.
macro.yield
Terminates a value-returning block and hands its SSA result back to the enclosing Vx expression.

Compilation Pipeline
Vx Compiler · MLIR Backend

How vxc compiles a block

A clean boundary between the host language frontend and MLIR passes
01 · EXPAND
Substitute Macros & Parse Header
The macro expander substitutes $t and $lanes tokens, parses inputs, returns, clobbers, and ensures, and keeps the MLIR body as raw text.
Surface AST → Expanded AST
02 · CHECK
Type, Borrow & Contract Check
Type-checks input expressions, records variable mutations from clobbers, and checks ensures against enclosing across loops. Emits InlineMlir in Flat HIR.
Expanded AST → Flat HIR (.vxlib)
03 · WRAP & VERIFY
Emit Private func.func
Wraps the body in func.func private @vx_flat_mlir_N, replaces macro.yield with return, runs MLIR’s parser/verifier, and audits every op against ensures.
Flat HIR → Verified MLIR Module
04 · INLINE & FUSE
Inline Body into Caller (-O1+)
At -O1 and above, vx-inline inlines the private wrapper (up to 200 ops) directly into the caller before loop fusion and vectorization.
Wrapper vanishes before lowering
What the Vx Frontend Sees
Typed input expressions, the return type, mutated variables (clobbers), and the ensures effect contract. The Vx parser never needs grammar rules for MLIR dialects.
What MLIR Passes See
Standard SSA operations inside an ordinary private function. No upstream MLIR pass had to be modified to understand "inline MLIR."

Why Customizing the Inliner Was Trivial
Our vx-inline pass is upstream MLIR’s Inliner with one threshold rule: it inlines a callee only when its body has at most 200 operations. That prevents compile-time blowup on deeply nested calls while guaranteeing every mlir! primitive inlines before loop passes run.

Cross-Call Optimization
Vx Compiler · MLIR Backend

The optimizer sees inside the block

Fusing three std::tensor calls into one affine loop—and the aliasing bug it exposed
Three library calls on 64×64 tensors 3 Loops → 1 Fused Loop 
// User Vx code: three separate std::tensor calls
a.fill(x);
b.fill(x);
let eq = a.compare(&b);

// After vx-inline + linalg-to-affine + loop fusion:
affine.for %i = 0 to 64 {
  affine.for %j = 0 to 64 {
    affine.store %x, %a[%i, %j] : memref<64x64xf32>
    affine.store %x, %b[%i, %j] : memref<64x64xf32>
    %va = affine.load %a[%i, %j] : memref<64x64xf32>
    %vb = affine.load %b[%i, %j] : memref<64x64xf32>
    // comparison accumulated in the same pass
  }
}
Source: Vx commit 4daa9662. With inline assembly, each call would remain an opaque loop boundary.
Why the Loops Fuse
Inline first, lower linalg to affine second
Tensor::fill and Tensor::compare are mlir! blocks written in linalg. Because vx-inline runs before linalg-to-affine lowering, the affine fusion pass sees all three loop nests in one block and fuses them into a single traversal.
War Story · What Broke Along the Way
Sub-view aliasing silently reordered matrix prints
Affine loop fusion initially compared memref SSA values without alias analysis. A matrix row read through a sub-view (memref.subview) looked like an unrelated buffer—so fusion sank the loop computing the matrix below the loop printing its rows!
The Fix: vx-fuse-and-tile-loops now fuses only when every memref in the function is a fresh allocation, a global, or a distinct reference parameter.

Atomics without compiler intrinsics

Implementing core::sync::atomic in library source with zero frontend intrinsics
stdlib/core/sync/atomic.vx Scalar & Tensor Element Atomics 
match order {
  AtomicOrdering::Relaxed => {
    return mlir!(
      inputs   : (%p = &mut self.v : !llvm.ptr, %x = val : $mlir),
      returns  : $t,
      dialects : ["llvm"]
    ) {
      %r = llvm.atomicrmw $op %p, %x monotonic : !llvm.ptr, $mlir
      macro.yield %r : $mlir
    };
  }
  AtomicOrdering::SeqCst => {
    return mlir!(
      inputs   : (%p = &mut self.v : !llvm.ptr, %x = val : $mlir),
      returns  : $t,
      dialects : ["llvm"]
    ) {
      %r = llvm.atomicrmw $op %p, %x seq_cst : !llvm.ptr, $mlir
      macro.yield %r : $mlir
    };
  }
  // Acquire, Release, AcqRel: one arm each
}
Zero Compiler Intrinsics
AtomicI8 through AtomicU64 in pure library code
Every load, store, swap, compare_exchange, fetch_add, and fence is an mlir! block wrapping llvm.atomicrmw or llvm.cmpxchg.
Why match on Ordering?
MLIR bakes memory ordering into op syntax
monotonic, acquire, and seq_cst are syntax keywords on llvm.atomicrmw, not SSA operands. A match selects the right block.
Constant-Folded Away at -O1+
One atomic instruction per call in optimized IR
When the caller passes a constant ordering like AtomicOrdering::SeqCst, inlining + constant folding eliminates the other four arms completely.

Generic blocks through macro substitution

Combining macro_rules with MLIR's vector dialect for portable SIMD
stdlib/std/tensor.vx · 4-way unrolled SIMD reduction Macro-Stamped MLIR Templates 
macro_rules stamp_tensor_sums {
  ($t : ident , $lanes : expr) => {
    impl Tensor<$t, [?]> {
      fn sum(self : &Tensor<$t, [?]>) -> $t {
        return mlir!(inputs : (%a = self : memref<?x$t>), returns : $t,
                     dialects : ["scf", "vector", "arith", "memref"]) {
          // Four vector<$lanes x $t> accumulators + scalar tail loop for remainder
          %x0   = vector.load %a[%i0] : memref<?x$t>, vector<$lanes x $t>
          %s0   = arith.addf %v0, %x0 fastmath<reassoc> : vector<$lanes x $t>
          %head = vector.reduction <add>, %acc fastmath<reassoc> : vector<$lanes x $t> into $t
          // ... scalar remainder loop + macro.yield %total : $t
        };
      }
    }
  };
}
stamp_tensor_sums!(f32, 16);   // 4 × vector<16xf32> = 64 floats/iter
stamp_tensor_sums!(f64, 8);    // 4 × vector<8xf64>  = 32 doubles/iter
1 · Textual Substitution First
$t and $lanes expand inside the mlir! body before MLIR parses it, producing concrete vector<16xf32> and vector<8xf64> types.
2 · Target-Agnostic SIMD
MLIR’s vector dialect and LLVM legalize vector<16xf32> to AVX-512, AVX2, or Arm NEON registers automatically.
3 · One Implementation
In C/C++, libraries maintain separate _mm512_*, _mm256_*, and vaddq_f32 loops. In Vx, it is written once.

Multi-Target Lowering
Vx Compiler · MLIR Backend

One block across CPU, GPU SMEM, and GPU HBM

Memory-space polymorphism and direct NVVM warp intrinsics
1 · One Atomic Block → Three Hardware Targets Memory-Space Polymorphic 
fn atomic_fetch_add_u32<M : Memory, D : Topology>(
    t : &Tensor<u32, [?], Memory::M>, idx : usize, val : u32
) -> u32 on(Topology::D) ensures(atomic(t)) {
  return mlir!(
    inputs  : (%m = t : memref<?xi32>, %i = idx : index, %v = val : i32),
    returns : u32,
    ensures : [atomic(t)],
    dialects: ["llvm", "memref", "arith"]
  ) {
    %base = memref.extract_aligned_pointer_as_index %m : memref<?xi32> -> index
    // address calculation → %ptr : !llvm.ptr
    %old  = llvm.atomicrmw add %ptr, %v seq_cst : !llvm.ptr, i32
    macro.yield %old : i32
  };
}
2 · GPU-Only Warp Vote + Popcount 2 PTX Instructions 
fn count_true(pred : bool) -> u32 on(Topology::Device) {
  return mlir!(inputs : (%p = pred : i1), returns : u32,
               ensures : [writes_only()], dialects : ["nvvm", "math", "arith"]) {
    %mask = arith.constant -1 : i32
    %b    = nvvm.vote.sync ballot %mask, %p : i32
    %c    = math.ctpop %b : i32
    macro.yield %c : i32
  };  // Lowers to: vote.sync.ballot.b32 + popc.b32
}

Operations like math.exp lower to fast hardware instructions on GPU and libm on CPU automatically. When a library needs target-specific ops (like nvvm.vote.sync), on(Topology::Device) or if comptime restricts or selects the block at compile time.

// Type mismatch inside the MLIR operations:
fn bad_popcnt(x : i32) -> i32 {

Second, vxc walks the parsed MLIR operations to verify that every memory access obeys the block’s ensures : [writes_only()] or ensures : [atomic(t)] clause—so an mlir! block cannot silently break Vx’s parallel race-freedom proof.

Current Limits
Vx Compiler · MLIR Backend

What does not work yet

Where the boundary between surface language and inline MLIR still has rough edges
1 · Line Offsets Inside the Block
Errors point to the block start
Diagnostics report the line and column where mlir!(...) begins, not the exact line inside a 40-line multi-accumulator reduction body.
2 · Raw !llvm.ptr Provenance
Pointer arithmetic is trusted
E8007 catches non-atomic memref.load/store, but once a block extracts an !llvm.ptr, the compiler checks the atomic op without proving the pointer offset came from %t.
3 · Producer–Consumer Channels
mbarrier needs ordered(t)
Hopper/Blackwell warp-specialized kernels synchronize shared buffers through mbarrier phases rather than atomic instructions. We are designing an ensures : [ordered(t)] clause for this.
4 · Host CPU ISA Selection
pause on x86 vs. yield on Arm
Topology::Current distinguishes Host vs. Device, but core::hint::spin_loop cannot yet branch on x86_64 vs. AArch64 inside one block.
5 · Pre-Inlining Wrapper Effects
llvm.intr.assume & buffer free
clobbers and ensures are checked by Vx, but are not yet emitted as MLIR MemoryEffects attributes on the private func.func wrapper before inlining.
6 · Transcendentals Without Hardware Ops
Porting LLVM libc in core::libm
Ops like math.asinh, acosh, and erf lower to libm calls in upstream MLIR. To stay libc-free on GPU, core::libm implements the polynomials in pure Vx + math.fma.

For Discussion

Open questions for the MLIR community

Four places where upstream idioms could help language frontends
Q1 Frontend Interop
A shared convention for inline MLIR blocks?
Any language that embeds MLIR text needs named SSA bindings, a result terminator (macro.yield), and declared side effects. Could MLIR-based frontends converge on a common syntax or dialect for inline blocks so editor tooling and verifiers can be shared?
Q2 Effects & Aliasing
Attaching argument memory effects to func.func?
What is the idiomatic way in upstream MLIR to translate a block’s clobbers : [self] and ensures : [writes_only()] into per-argument memory and alias attributes on the private func.func wrapper so bufferization and deallocation passes respect them before inlining?
Q3 Source Locations
Mapping diagnostic spans through macro-substituted MLIR?
When parseSourceString parses an inline block after $t and $lanes macro expansion, what is the cleanest way to feed a base FileLineColLoc offset into the MLIR parser so errors point to the exact line in the .vx source file?
Q4 Target Dialects
Portable target hints without duplicating blocks?
Operations like math.ctpop and llvm.atomicrmw lower cleanly across x86, Arm, and NVVM. Where should target-divergent hints like spin-loop pause / yield or GPU mbarrier phase operations live so library authors don’t drop back to per-ISA strings?
