# Dijkstra Memory Algebra Fix

## Implementation Plan

### Goal
Fix the stack overflow error that occurs during compilation of implicit multi-hop memory transfers (e.g. `tests/frontend/pass/transfer_cost_advanced_dijkstra.vx`).

### Context
When transferring data between memory spaces that do not have a direct hardware path (e.g., `NPU_HBM` to `Remote_HBM`), the compiler's `transfer_cost_graph` uses Dijkstra's algorithm to compute the shortest path. It rewrites the single `transfer(..., Remote_HBM)` into nested transfers like `transfer(transfer(..., NicRam), Remote_HBM)`. 
When evaluating the generated intermediate transfer, its memory space (`NicRam`) falls back to the parent `Topology::NPU`. Due to this topology fallback inside `Type::Pinned`, when the compiler extracts the type's memory space, it incorrectly yields `NPUHBM` instead of `NicRam`. This incorrect extraction triggers another path evaluation from `NPUHBM` to `RemoteHbm`, creating an infinite recursion loop and causing a stack overflow.

### Proposed Fix
Modify `src/sema/expr.rs` to extract the memory space directly from `TransferExpr.space` instead of the typed expression if the inner expression is a compiler-generated nested `Transfer`. This preserves the exact explicit `NicRam` target across synthetic recursive checks, properly terminating the path expansion.

## Walkthrough

The fix cleanly isolates the issue by preventing loss of memory topology resolution during recursive type checks.
1. The compiler now looks at explicit nested `TransferExpr` AST nodes generated by the compiler's synthetic multi-hop path resolution.
2. If it is an explicit transfer, it extracts the exact `MemorySpace` directly (e.g., `NicRam`).
3. This prevents `transfer_path` from recalculating the route from `NPUHBM` back to `Remote_HBM`, immediately returning a 2-hop sequence that terminates the `do_rewrite` recursion.
4. `cargo test` passes successfully, and `vxc --action print-ast` correctly evaluates the full topology without crashing.
